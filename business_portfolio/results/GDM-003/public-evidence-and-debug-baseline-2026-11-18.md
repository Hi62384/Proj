# GDM-003 public evidence and debug baseline — 2026-11-18

## Public technical evidence

- A Godot issue for versions 4.2.2 and 4.4 describes a dependency available on `PATH` that did not load; a maintainer explained the restricted search behavior for that context. This is consistent with the earlier owned-fixture observation, but it does not establish every Windows loader configuration. [Godot issue #104543](https://github.com/godotengine/godot/issues/104543)
- A separate report tested Godot 4.6 and a 4.7 development build and describes dependencies failing to load even when supplied. It was open and awaiting assessment in the page consulted; the report has not been independently reproduced here and does not establish that Godot 4.7.2 stable has the same defect. [Godot issue #118485](https://github.com/godotengine/godot/issues/118485)
- An older Godot 4.3 report attributed missing export dependencies to a descriptor-format mistake; a contributor supplied the dictionary format and the reporter closed the issue. This is a concrete configuration example, not a count of potential buyers or evidence of willingness to pay. [Godot issue #96325](https://github.com/godotengine/godot/issues/96325)
- Microsoft's Xbox Godot sample provides free troubleshooting that distinguishes an absent extension library from an error-126 dependency load failure. Its context is the Xbox/GDK sample, not a general packaged-build verifier. [Microsoft sample troubleshooting](https://github.com/microsoft/XBOX-Godot-Sample/blob/main/docs/troubleshooting.md)
- The Godot CEF project documents a plugin-specific preflight for CI and notes export-validation limitations. It is a relevant free, specialized alternative for its own browser runtime, not evidence of a generic competing product or its sales. [Godot CEF runtime installation](https://godotcef.org/api/runtime-installation)

These sources support the existence of technical problems and available guidance or specialized tooling. They do not quantify current demand, demonstrate that this project's tool would fix a reported issue, establish paid conversion, or prove that Godot 4.7.2 behaves identically to older reports. They do not by themselves pass the project's material-differentiation gate.

## Owned debug-versus-release comparison

The [Godot 4.7.2 Windows source](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/windows/os_windows.cpp) includes a debug-only missing-dependency diagnostic in the dynamic-library error path. To test the observed behavior, the owned fixture was exported using the matching Windows x64 debug template. The clean debug game loaded the extension. With `leaf.dll` removed, it returned process exit 0, reported the extension not loaded, and named `leaf.dll` in its error-126 diagnostic. This gives developers a free diagnostic in that tested debug configuration; the earlier release fixture did not name the leaf in its error.

When the clean debug export directory was added to `PATH` but the file remained absent from the package under test, the debug game still failed to load while its error no longer named `leaf.dll`. Dependencies resolved the leaf from the external directory; the fixture-specific free helper reported that outside-package resolution as unknown. This is one controlled observation, not a complete description of Godot's or Windows' search behavior. It supports retaining package/host uncertainty, not claiming a product can guarantee loader behavior.

The fixture builder has an optional matching debug-template argument and a debug-diagnostic test script. A fresh complete builder run with the debug template succeeded; its three debug diagnostic tests and twenty-one fixture integration tests passed. The current product spike remains release-fixture-oriented and must not present these debug observations as supported general debug analysis. No outreach, spending, publication or sale occurred.
