# GDM-001 isolation and baseline review — 2026-11-18

## Observed local evidence

The current Unity prototype executes `IAsyncSaveAdapter` inside the Editor process. Its deadline signals cancellation and deliberately waits for the returned task before deleting the fixture copy. The 40-test checkpoint demonstrates that behavior, not a bounded hard timeout. The adapter can use the Editor's filesystem and network permissions, and work started outside its returned task can outlive it. The fixture copy and path checks do not enforce a security boundary. Use synthetic fixtures and trusted code only.

The native `HistoricalSaveTests` exercise the same three synthetic files, directly assert shield, potions and quest state, and demonstrate a named NUnit failure for the deliberate v1 inventory loss. `ManifestAndCopyTests.RunnerDetectsSilentLossAndPreservesSource` runs the same v1 loader with an async `Task.Yield` adapter and detects the shield loss. These are useful partial observations, not the specified head-to-head benchmark: the native and prototype tests do not cover identical asynchronous scenarios and two deliberate failure types, setup and maintenance times were not measured, and neither proves isolation or a release advantage. The sample loader is synthetic and does not model a real game's profile writes.

## Isolation options and limits

A separate process would permit an external supervisor to terminate a stuck worker, but killing one process does not itself terminate its children. Microsoft documents Windows Job Objects for managing associated processes as a unit, with documented child-association exceptions and breakaway behavior. A job is not, by itself, filesystem or network confinement; security limits apply to processes separately. Sources: [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [Terminating a Process](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process), [Job Object security](https://learn.microsoft.com/en-us/windows/win32/procthread/job-object-security-and-access-rights).

Microsoft describes AppContainer as controlling filesystem, registry, network and process access through an isolation boundary and capabilities: [AppContainer isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation). This is a candidate for a Windows-specific experiment, not evidence that Unity Editor, its package manager, licensing, game loaders, or native plugins run correctly within it. Editor startup dependencies, explicitly granted paths, inherited handles, process creation and cleanup must be tested. No security guarantee follows from starting another Unity process under the same user. Cross-platform confinement remains unresearched and unsupported.

## Proposed trusted integration boundary

The only supportable initial claim is a regression check for an owner-supplied, reviewed game build and adapter that are trusted to perform the requested restore and report the state honestly. The supervisor, its configuration and pinned fixture hashes must also be trusted. An OS-restricted worker is a damage-limiting measure, not a trusted observer of adversarial code in its own process. A compromised or dishonest game, adapter, loader, engine, supervisor or host can forge outcomes; this proposal does not detect that compromise. No customer code or arbitrary save should be run on the basis of this proposal.

A production implementation would need to bind each run to the exact reviewed player build, adapter, assertion definitions and fixture bytes; reject mismatched identity before launch; launch with no inherited handles, only explicitly required capabilities, a private scratch profile, a hard deadline and a controlled process tree; and independently verify input identity, exit, completion, report schema and bounded output before publishing a result. Those checks constrain substitution and malformed reports only under a trusted host and protected configuration; they do not prove that state was restored. A pass must mean the named trusted integration reported matching state, not that a hostile integration was verified. Timeouts, crashes, missing or malformed output and untrusted integrations must never become passes. A report must distinguish worker claims from supervisor observations, and expose no save values by default; IDs and property paths can still be sensitive.

This is a proposed contract, not an implemented production boundary. The current experiment pins fixture bytes and checks report shape and exit status, but does not bind the whole player or adapter, protect configuration against a hostile host, implement a general capabilities policy, or independently authenticate restoration. The retained v13 forgery is now a repeatable test: the default decision is untrusted; explicitly asserting trust makes the fabricated pass structurally acceptable. Real cross-platform sandbox behavior, build provenance, race resistance and recovery need separate evidence.
