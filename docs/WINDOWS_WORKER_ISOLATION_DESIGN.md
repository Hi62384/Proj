# Windows worker isolation: candidate and acceptance gates

Status: research only. No Windows worker backend is enabled by this document or its host-side tests.

## Pinned failure boundary

The installed executable reported `codex-cli 0.162.1`. In the corresponding [`rust-v0.162.1` home-dir source](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/utils/home-dir/src/lib.rs), `find_codex_home_from_env` validates an explicit `CODEX_HOME` and invokes `PathBuf::canonicalize`. The unset path uses `dirs::home_dir`. The disposable app-server probe observed access denied in the former and no profile home in the latter, before its initialize response. A successful `--version` does not test this path.

In the corresponding [exec source](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/exec/src/lib.rs), `codex exec` applies `canonicalize_existing_preserving_symlinks` to an explicitly supplied working directory. This is a separate command path, not proof that app-server uses the same call site. App-server thread/start and config-layer working-directory handling remain to be traced against a pinned revision after its initial home failure is overcome. The [upstream report](https://github.com/openai/codex/issues/45871) identifies `CreateFileW` followed by `GetFinalPathNameByHandleW`: NT-volume naming succeeds in its reproduction, while DOS-volume naming fails. The targeted disposable AppContainer probe below reproduced that distinction on this host.

The pinned [absolute-path utility](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/utils/absolute-path/src/lib.rs) makes an important distinction: `AbsolutePathBuf` is normalized but does not promise a canonical or existing path, and `canonicalize_existing_preserving_symlinks` deliberately preserves some logical symlink paths while propagating canonicalization failures. Consequently, returning an NT device path is not a drop-in replacement for that function or proof of authorization. Its compatibility with Windows path parsing, policy matching, child-process cwd and logical symlink behavior must be established separately. The pinned app-server library imports `find_codex_home`; the exact thread/start cwd call chain is still unverified.

The pinned [app-server startup](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/app-server/src/lib.rs) calls `find_codex_home` before constructing `ConfigManager`, loading startup config and initializing authentication. The [config manager](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/app-server/src/config_manager.rs) separately converts `codex_home` and session cwd to `AbsolutePathBuf` when loading session layers, and passes cwd through further config rebuilding. This establishes consumers, not their complete downstream behavior; thread-start and command execution still need tracing and actual protocol testing.

## Candidate for review, not a patch

Investigate an upstream-supported Windows path resolver that opens the actual directory and obtains its resolved NT-volume name from the handle. Keep the handle alive for any security-sensitive operations, or use another demonstrably race-resistant operation that binds use to the validated object. Investigate whether downstream Codex APIs accept such a name and preserve its required path semantics. A handle-derived name alone is not a capability: validating its string, closing the handle, then reopening a user-controlled path leaves a junction-retarget race. Do not substitute lexical absolutization, assume prefixes imply containment, or change global Windows namespace ACLs.

Keep separate trust domains: a private per-worker Codex home and authenticated model process with only necessary outbound connectivity; narrowly scoped workspace exchange; and a network-disabled execution container for project tests. The current Python fixture proves only a limited read/write boundary, not complete worker isolation. Determine how the model subprocess is prevented from spawning unsandboxed children, leaking credentials, accessing other workers' homes, or escaping network and filesystem restrictions before deployment. Windows job objects can bound resources and cleanup but do not replace access controls. A candidate must fail closed if any restriction or health check cannot be established.

## Required regression cases

| Area | Positive control | Adversarial or failure control |
| --- | --- | --- |
| Home and working directory | Existing permitted directory resolves; initialize, thread setup and a bounded synthetic task succeed | Missing/file path, outside directory, sibling with matching text prefix, parent traversal, junction/symlink escape, junction retarget between validation and use, mixed case and volume changes must not grant access; errors fail closed. Test home and each actual app-server and exec cwd call site separately. |
| Files and credentials | Approved fixture is readable, scoped output can be handed back | Outside and broadly shared fixtures, another worker's home and credentials denied; test read-only files cannot be modified, renamed or deleted, including through hard links and reparse points. |
| Network | Required model endpoint reachable from the model process | Test process cannot reach loopback, LAN or internet, including child processes; host-side positive controls prove listeners/endpoints work. Confirm no credential forwarding to tests. |
| Execution lifecycle | Passing and failing Python and JavaScript tests classified correctly | Time/memory/process limits, cancellation, descendants, controller crash, orphan cleanup and startup failure leave no running process or accessible worker credentials. |
| Coordination | Concurrent workers receive separate homes, state and staged projects | No cross-worker reads/writes, stale output acceptance, accidental modification of original project, or cleanup outside an owned temporary root. |

The lightweight `portfolio_manager.tests.test_windows_path_identity_probe` checks on the host that an NT handle path resolves a disposable junction and that a newly opened handle observes a retargeted junction. Separately, `python -m portfolio_manager.tests.live_windows_isolation --path-api-only` uses a disposable AppContainer and a private Python copy to inspect an ordinary directory and a junction targeting it. On this host, NT handle resolution returned the same target for both; DOS handle resolution failed for both with error 5. The probe verified its child had an AppContainer token and cleaned up its profile and junction. These are research controls only: they do not implement a containment check, prove race resistance, establish downstream Codex compatibility, or verify an actual worker. The next targeted work is to trace app-server cwd/config paths and design a reviewed, handle-bound use of the NT identity before building a candidate. Any build should use reviewed pinned source and dependencies, be isolated from the installed executable, and run only when resource headroom is sufficient.

Further disposable tests found: a retained handle continued to identify its original target after a junction was retargeted, while a new open observed the new target; a missing directory and an outside file opened for read were rejected inside the AppContainer (errors 2 and 5). On the host, the raw `\\Device\\...` form was rejected as a Win32 working directory. Inside the container, the corresponding `\\?\\GLOBALROOT\\Device\\...` form was accepted as cwd and a relative read of a synthetic marker succeeded, but Python's strict realpath still failed with error 5. This demonstrates a limited representation that Win32 can use; it does not bypass or fix Codex's canonicalization, prove Codex accepts the representation, or prove protection from reparse races. Any design using `GLOBALROOT` needs explicit security review because it addresses the device namespace; access-control enforcement, containment and path-policy behavior must be independently tested rather than inferred from this success.

## Handle-relative research prototype and review

`portfolio_manager/tests/windows_path_research.py` is a separate, test-only prototype. It retains a directory handle and uses `NtCreateFile` with `RootDirectory`, a single child component, `OBJ_DONT_REPARSE`, and explicit reparse-attribute rejection. [Microsoft's API documentation](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile) describes the relative-handle operation. Host tests confirmed that opening the child relative to a retained root continued to identify the original child after the root's old path was replaced, and rejected a junction and malformed components. A disposable AppContainer run confirmed the ordinary child identity matched and an escape junction was rejected. These are narrow observations, not a security certification.

Review finding: the prototype is **not suitable for authorization or worker use**. Its initial root open follows reparse points, the returned child identity is not a retained child capability, and its string cwd can reopen a replacement object. It does not implement file reads/writes, multi-component traversal, concurrent attack resistance, hard-link policy, name/case semantics, unsupported-filesystem handling, or inheritance into process creation. A safe design must provision and validate a trusted starting handle, walk one component at a time without following reparse points, retain and use the resulting handles for sensitive operations, and enforce OS isolation independently. Even that does not solve standard Windows process APIs that accept cwd as a string; proving an immutable owner-controlled staging tree or another reviewed approach is necessary before claiming race resistance. The experimental implementation deliberately never changes Codex or the live worker.

Required next work includes tracing the precise pinned thread-start/config/command path consumers and evaluating a handle-bound broker versus immutable staging under an independently enforced AppContainer. Then a reviewed candidate must pass the entire acceptance matrix above, including authentication, actual app-server initialization, model access, cancellation and network tests. No Codex build or full-worker test has been run with this prototype; a reviewed candidate and sufficient build resources remain prerequisites.

### Retained traversal and initial-anchor proposal

The research helper can now retain the child handle and walk multiple individual components. A host test deliberately replaces an intermediate directory after it is opened; the next open still reaches the original child. A disposable AppContainer test walked two allowed components and rejected an escape junction. The helper closes intermediate handles on success and failure; the caller closes the final handle. These cases do not establish safety against all races or filesystems.

Proposed bootstrap: the trusted controller, before launching a worker, must obtain a handle to an owner-controlled parent through a verified non-reparse chain from a known OS anchor; create a unique per-run directory beneath it; verify the actual handle identity and effective security descriptors, including parent delete/rename rights and inheritance; then keep the trusted handles open and pass only the appropriate restricted capabilities to the worker or broker. Failure of any step must prevent launch. This depends on proving how the first anchor is acquired without a reparse race and how Windows owner and AppContainer-token access interact on this machine. The current `DirectoryHandle(path)` follows an initial path and does none of that validation, so it is explicitly not an implementation of the bootstrap.

For subsequent I/O, a potential broker can resolve one component at a time relative to retained handles with no reparse traversal and perform I/O through the resulting handle, not return a checked path to be reopened. Review must cover hard links, case-sensitive directories, alternate data streams, device names, filesystem changes and cleanup. The model process and native process launcher still accept strings: holding a handle while passing `GLOBALROOT` as cwd does not bind the launch to it. Before any integration, prove that the owner-controlled staged tree cannot be renamed, replaced or redirected by any worker process for its lifetime, or establish another supported binding. The actual Codex path consumers cannot simply call the current helper: config and runtime interfaces exchange path values, and the helper does not solve their canonicalization or process-creation behavior. No integration patch is enabled or ready for deployment.

### Identity-checked read experiment

The test-only helper now accepts a separately supplied expected volume/file identity when opening a child directory or reading a file relative to a retained parent. The file experiment rejects reparse points, multiple hard links, identity mismatch and oversized content, and reads from the opened handle. Host tests exercised successful reads and rejection of replacements, hard links and oversized data; the synthetic AppContainer test exercised a successful identity-checked read and size limit. The test expected identities were obtained from test fixtures; **the prototype does not establish a trusted identity source, validate initial-root ACLs, or prove the root cannot be changed by a worker**.

A separate adversarial test demonstrated that a file can be modified in place while its identity stays the same. Therefore identity checks are not content integrity: a production design additionally needs OS-enforced read-only access and/or verified content hashes and a suitable consistency model. Link count is only a conservative rejection condition, not proof of trusted provenance. Concurrent writes, unusual filesystems, identity reuse, alternate streams and staged-tree lifecycle remain unverified.

Windows [`CreateProcessW`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw) takes `lpCurrentDirectory` as a string, not a directory handle. A concrete integration therefore needs a staging namespace whose full ancestor chain cannot be renamed, replaced or redirected by any worker token for the entire process lifetime, plus independently enforced filesystem restrictions and a reviewed way to get Codex past its strict home-path resolution. No proposed broker is enabled, no such namespace has been verified, and the existing tests are not a substitute for end-to-end worker isolation.

### Disposable namespace protection experiment

The opt-in `--namespace-only` probe creates a synthetic read-only stage and tries file writes/deletes and directory renames from the AppContainer, then checks the actual content and paths from the host. With only the stage's immediate parent protected, file changes and stage rename were denied but the container **could rename that protected parent** through rights on its writable parent. Holding the protected parent open without delete sharing did not prevent that rename in this test. This rules out treating either a child ACL or this particular retained handle as sufficient to protect the cwd path.

With `--namespace-only --protect-profile-root`, the probe additionally removes inherited permissions from the disposable profile staging root and grants its specific AppContainer read/execute, while retaining owner and System full access for setup/cleanup. In that limited configuration the container was denied file changes, stage rename and immediate-parent rename; host checks confirmed the stage content and paths remained unchanged. The temporary profile was removed. This is evidence for protecting a chain, not proof of a complete immutable namespace: replacement of higher ancestors, inherited handles, other rights and filesystem types have not been examined. The test does not model a malicious process with the host owner's unrestricted token. The real bootstrap still needs to establish and verify a trusted anchor, ACLs and non-reparse ancestry, prove all relevant parent delete/rename rights, and distinguish the model process's writeable private home from the read-only test namespace. No live ACL was modified.

The deeper opt-in `--protect-profile-parent` check exposed an existing full-control package entry on the unique temporary profile parent. Adding a read/execute grant with `icacls /grant:r` did **not** remove that other entry: the isolated process could request DELETE on the staging root. In the experimental `--replace-parent-grant` variant, the probe removed the old package grants on that disposable parent before applying read/execute. The isolated process then received access-denied when requesting DELETE on the staging root and DELETE_CHILD on its parent. Read-only DELETE and DELETE_CHILD requests for seven successive higher ancestors also returned error 5; these are access-request observations, not proof against all replacement methods or filesystem semantics. Host checks confirmed the stage was unchanged and its immediate parent had not moved. The test profile alone was modified and removed afterward.

The same synthetic split-layout probe now also asks for WRITE_DAC and WRITE_OWNER on the staging root, and WRITE_DAC on its profile parent; each request was denied without modifying the descriptor. Separately, `windows_anchor_acl_research.py` reads one already-open folder handle's owner and DACL, rejects a mismatched identity, unexpected or inherited ACEs, excess rights and missing required entries, and requires that the final component was opened without following a reparse point. Disposable tests covered the expected explicit ACL and rejection of a broad Everyone entry. This narrow descriptor check does not prove effective token access, owner provenance, integrity labels, ancestor integrity, race resistance or a trustworthy initial path, and is not used for authorization or in the worker.

The ACL research now also walks from a supplied open root through individual no-reparse child handles, retains them during the audit, and checks each expected identity and descriptor. Disposable tests rejected a changed child DACL and a junction even when its target's identity was supplied. This still assumes the first root handle and policy values come from a trusted source and does not prove that another process cannot modify permissions later. It is not a production bootstrap.

This result makes ACL construction and effective-token verification a required preflight, rather than assuming a named grant replaced every existing entry. A real integration must additionally inspect owner, ACL and reparse status through a race-resistant trusted anchor, verify no unwanted package or capability grants and no writable ancestor under its threat model, and repeat negative operations under the exact worker token. The model's separately writable login/config location, file-ID provenance and process creation remain unresolved. Codex still fails before initialization when canonicalizing its home; these namespace checks do not fix that startup call. Never copy this experimental ACL recipe onto an existing profile or shared directory.

### Synthetic split-layout experiment

The opt-in `--namespace-only --protect-profile-root --protect-profile-parent --replace-parent-grant --split-layout` adds a separate synthetic runtime folder beside the protected staged project. The disposable setup clears package grants on that runtime folder, grants the package read/execute and write at the folder itself, and grants inherited modify rights to children; owner and System retain full access for setup and cleanup. No real login or credentials are used. The worker test created, updated and deleted a file and subdirectory, created and reopened a small SQLite database in WAL mode, and could not rename the runtime root. It could not change or remove the staged fixture, rename the stage or its immediate parent, or create a hard link to the staged fixture. The host verified the staged content was unchanged.

The trusted test setup supplied expected stage and file identities, the isolated process matched them using handle-relative opens, and a deliberately wrong stage identity was rejected. This models identity transport from a trusted provisioner; it does not establish a production trusted anchor or prevent a compromised process from skipping its own checks. Production enforcement belongs in a trusted controller/broker and in OS permissions. The individual ACL entries are an experiment on a unique temporary profile, not an integration recipe: do not apply them to an existing user profile. SQLite success does not establish that Codex authentication, logs, all database recovery cases, or arbitrary test runtimes work. A model process with Internet Client and writable authentication data also needs a separate network-disabled test process with no inherited credentials, separate access rights and validated child-process handling. No real authentication was copied or exercised.

The remaining direct startup dependency is still the pinned Codex `find_codex_home` canonicalization discussed above; the split layout cannot initialize the current app-server until that call and its downstream cwd/path consumers have a reviewed fix. Actual app-server startup, protocol negotiation, authentication, model turn, Python/JavaScript test execution, isolation escape attempts, failure cleanup and cancellation remain required before this can be called a complete worker.

The additional opt-in `--two-profiles` probe creates a second disposable AppContainer identity with no network capability. The first identity could read a fictional private-runtime fixture; the second could read the approved staged fixture but was denied the private-runtime and outside fixtures and could not modify the staged file. A local server was reachable from the host both before and after the second identity's loopback attempt, which failed. Both test profiles were deleted. This demonstrates limited identity and loopback separation only: it does not prove internet/LAN blocking, descendant containment, credential isolation in an actual model session, or a working Windows test runner. The synthetic `cmd.exe` probe is not a Python or JavaScript project test.

The synthetic child launcher now supplies an explicit allowlist of ordinary Windows environment variables rather than inheriting the full parent environment. A fictional canary was visible to an unrestricted host control and absent from the restricted synthetic test child; the fictional app-server separately rejected that canary if present. The allowlist includes ordinary profile paths required for this host's AppContainer startup; this is not a proof that production credentials, handles, environment values or filesystem contents cannot leak through other channels.

The disposable process launcher now supplies an explicit Windows inherited-handle list containing only its output pipe. In the separate test identity, an intentionally inheritable synthetic event could not be signalled; a host child using unrestricted inheritance signalled that same event as a positive control. The private-runtime read and staged-write denials and loopback check still passed. The experimental app-server launcher separately lists only its three standard-stream handles; a fictional local protocol server verified stdin, stdout, stderr and exclusion of the synthetic event. An earlier probe incorrectly compared handle numbers, which may be reused for different objects; it was replaced by the event-object signalling check. Neither launcher is integrated into the real worker. Production still needs tests for actual credentials, unrelated controller handles, descendants, concurrency, cancellation and launch failure.

### Reviewable launch-contract prototype

`portfolio_manager/tests/windows_worker_launch_research.py` models an integration seam without changing Codex or the worker: a trusted provisioner supplies expected parent, home and workspace identities; the prototype rejects a reparse point at the parent's final component, verifies its identity, opens home and workspace relative to the retained parent without following reparse points, verifies their identities and retains the handles. It allows only a bounded identity-checked synthetic workspace read. `launch()` always fails closed. The associated host tests cover parent and workspace replacement, junction substitution, retained-handle lifetime, successful synthetic reading and refusal to launch. Intermediate ancestors, the trusted provisioner, actual token/ACL validation and content consistency are not established; caller-supplied identities alone are not a security boundary.

Concrete integration map to review after those prerequisites exist:

1. `portfolio_manager/runner.py` would select a new explicit Windows backend and request a provisioned split layout, rather than silently falling back from the existing WSL path. Its lifecycle must own handles and cleanup through cancellation and controller failure.
2. `portfolio_autopilot/codex_relay/codex.py` currently starts the app-server with a string `cwd` and sends a string workspace in `thread/start`. A reviewed upstream-compatible home/cwd resolver and a protected process-launch contract must be available before replacing either. Merely converting a validated handle back into a string reintroduces the replacement race.
3. `portfolio_autopilot/codex_relay/permissions.py` must require affirmative Windows filesystem, network and process-boundary negative controls before calling a sandbox verified; an echo-only check cannot prove isolation. The model process needs its private writable home and narrowly scoped network, while verification processes need a distinct network-disabled token without access to authentication.
4. The current WSL-specific `BubblewrapVerifier` needs a separately reviewed Windows verifier, with Python and JavaScript tests against read-only staged inputs, process-tree limits, timeout, cancellation, tamper checks and trusted output handoff. Passing the synthetic layout alone is not that verifier.

`python -m portfolio_manager.tests.windows_worker_acceptance` runs the fictional protocol-server, split-profile and process-lifecycle probes and always reports `not_ready` for the real worker. It rejects missing markers and failure exits. The lifecycle experiment creates a Windows job with kill-on-close, starts a synthetic process suspended, assigns it to the job before resuming, observes its synthetic child in the job and confirms both exit when the job closes. A separate probe repeated that test with both processes confirmed to have AppContainer tokens. Host and AppContainer job memory tests each rejected a 64 MiB synthetic allocation under a 48 MiB per-process limit. This is not yet integrated with the worker, does not prove CPU limits or aggregate memory enforcement, and does not remove profiles after an abrupt controller crash.

The research acceptance controller now creates and owns its exact randomly named temporary profiles, places each synthetic probe in a kill-on-close job atomically during process creation, and waits for the observed owned process tree before deleting those profiles. A forced-timeout test checked that the process tree stopped and that only the two owned profile names could be re-created after release; an additional disposable controller-termination test observed its parent and child exit. If termination cannot be verified, the acceptance runner fails closed, retains its own profiles and reports their identifier instead of deleting them.

The controller writes a crash-visible journal under the checkout's `.tmp/portfolio-acceptance-profile-journals`, marking each create or delete as pending until confirmed. A synthetic crash test stopped only its own test controller, verified its exact PID, identifier and two confirmed profile names from the surviving journal, then deleted only those names. The test uses the base Python executable directly because the venv launcher can introduce a different PID; an earlier failed test left a journal, and its two known profiles were cleaned only after their actual owner exited. Automatic stale-journal recovery is **not implemented**: PID reuse, live-session locking, journal/ancestor integrity, a crash during a pending API call and filesystem residue still require review. Ambiguous pending entries are not authorization to delete. Do not scan for or delete other sessions' profiles.

Version-2 research journals now hold a separate byte-range lock for the owner's lifetime. A read-only inspector refuses live locks, pending operations, malformed records, foreign names and unknown/live owners; a stopped owner with a syntactically valid record is still classified `requires_proof`, and the inspector never deletes profiles. A live crash test exercised this conservative inspection before cleaning the two profiles whose exact provenance was independently known to that test. Automatic stale cleanup remains blocked: a caller-supplied owner check or an unlocked, valid-looking file cannot establish journal provenance or rule out live processes using those profile identities. An interrupted create/delete remains ambiguous. No other session's profiles are scanned or deleted.

The acceptance runner's combined owned-profile checks passed after these changes, and the focused owner, journal, process, path and ACL tests passed. No incomplete test journal remained after the verified runs. These results cover only the synthetic controller; production recovery must also handle machine shutdown, inaccessible journals, profile deletion failure and independently verified ownership without disrupting another live session.

The pinned Codex home resolver currently calls `PathBuf::canonicalize`; a protected-layout proof cannot be expressed by an unchecked environment variable or lexical fallback. A real source change would need an authenticated process-local capability or protected-layout contract at the resolver and every cwd consumer, preserving existing behavior outside this mode and rejecting missing proof. How to convey that proof through the app-server protocol and string-only Windows process API has not yet been designed or implemented. Building this research contract does not produce or install a patched Codex executable.

For a source review, the first affected call is `find_codex_home_from_env` in `utils/home-dir/src/lib.rs`, followed by the app-server's `ConfigManager` and its cwd/config consumers. A possible upstream interface would add a distinct Windows-only protected-layout context, constructed from explicitly inherited directory handles and identities provided by a trusted launcher, instead of accepting an ordinary environment string as proof. The existing canonicalizing branch would remain unchanged for ordinary invocations. The context must retain handles and be backed by independently verified ACL/ancestor immutability for any unavoidable path-based consumer; accepting a handle without validating its provenance and access constraints is insufficient. Every config, authentication, cwd and child-process consumer must be audited before this could preserve the existing security contract. This is a proposed interface, not a complete patch: the proof transport, trusted bootstrap and full consumer audit are missing, so no alternate home-resolution branch has been implemented or enabled.
