# GDM-003 Godot and free-tool baseline — 2026-11-18

## Setup and actual observations

An owned, minimal C GDExtension fixture was built with MSVC 14.44, using the separately obtained Godot 4.4 C interface header. Its initialization calls an owned static chain: `extension.dll` → `root.dll` → `middle.dll` → `leaf.dll`. Godot 4.7.2 stable editor and matching Windows x64 release template were downloaded from the official release; their archive SHA-256 values matched the official release metadata (`731980f9608d61333e5baf54a2ef17210acc7a538446c0cb9969f002aca1e953` and `f298490b8d44d934be425a5a65a51bf15f422428b229a06a6e11d9ffea248011`). Dependencies v1.11.1 was downloaded from its official release; its archive hash was `7d22dc00f1c09fd4415d48ad74d1cf801893e83b9a39944b0fce6dea7ceaea99`, but no publisher-provided digest was verified. These third-party files are not included in the public result or product sources.

Godot `--headless --editor --path <project> --import` and `--headless --path <project> --export-release "Windows Desktop" <output>/fixture.exe` returned 0. The editor emitted an unrelated root certificate store error in this sandbox. With all three dependencies declared in `[dependencies]`, the actual exported directory contained `fixture.exe`, `fixture.pck`, `extension.dll`, `root.dll`, `middle.dll`, and `leaf.dll`, all at the output root. The descriptor remained inside the PCK; a literal check for the original `res://addons/fixture/bin/extension.dll` relative to the exported directory would incorrectly flag the clean export. Running this owned clean export headless printed `GDM-003 loaded: true` and exited 0.

Independent copies of that export were modified after export. Removing `root.dll` or `leaf.dll` caused Godot to report error 126 for `addons/fixture/bin/extension.dll`, then `GDM-003 loaded: false`. Replacing `extension.dll` with an owned x86 DLL produced error 193 and `loaded: false`. Removing `extension.dll` reported the extension library missing and `loaded: false`. Each program still exited 0, because the fixture script deliberately quits normally; these exit codes do not imply Godot or all games always behave this way. The x86 replacement also lacks the entry symbol, so that case does not isolate every possible cause beyond the observed architecture-related loader error.

In a separate project copy, `leaf.dll` was removed only from the descriptor's `[dependencies]` dictionary while remaining present in the source bin. Export returned 0 and staged the other DLLs but not `leaf.dll`; the run emitted the same error 126 and `loaded: false`. The export log did not name the missing leaf; it did contain the certificate-store error. This is one controlled omission, not a survey of Godot versions or export settings.

In another project copy, only the release library entry was changed to a nonexistent path. Godot's export returned 1 and its log named the missing `not-there.dll` and the failed copy; it nevertheless left an executable and PCK in the output directory. A caller must check the export status and should not mistake those partial artifacts for a successful export.

## Dependencies and the DIY challenge

`Dependencies.exe -json -chain -depth 4 <export>/extension.dll` returned 0 for the clean, missing-direct, missing-transitive, wrong-architecture, and omitted-declaration cases. In the clean JSON, all three fixture chain nodes resolved. In the direct case, `root.dll` had a null `Filepath`; in the transitive and omitted-declaration cases, the chain reached `leaf.dll` with a null `Filepath`. The clean chain also included unresolved host/system-related names; interpreting every null as a definite missing shipped DLL would produce misleading results. The wrong-architecture replacement was analyzed as an x86 root and resolved system imports under `SysWOW64`; this run did not establish that the CLI warns about the mismatch with the intended x64 game.

A small, explicitly fixture-specific Python script used the Dependencies JSON plus the source descriptor and source bin: for the omitted case it printed `extension.dll -> root.dll -> middle.dll -> leaf.dll | declared in fixture dependency map: False`; for the post-export deletion it printed the same chain with `True`; for the clean case it found no unresolved import matching a source-bin DLL. It is not a general parser or loader model, does not inspect a PCK, handle general feature tags, recognize architecture, or model runtime-only loads. Diagnosis time and implementation effort were not measured. The free tool and small script reproduce the useful explanation for this one case, materially weakening the proposed product differentiation, but they do not establish equivalence across the full promised cases. A go/kill decision remains open pending a fair, time-bounded comparison across the specified cases and a reliable staging/feature model; no product implementation or commercial value is claimed.

Reproduction inputs and limitations are in `products/game-tools/native-dependency-verifier/fixture/README.md`. The experiment ran only owned fixture binaries and downloaded tools locally. No spending, publication, customer contact, sale or clean-machine test occurred. Windows system and dynamic-load behavior remain host dependent.

Portfolio verification after this checkpoint: browser build and `--check` and commercial checks passed. The 94-test portfolio suite had one failure and one skip: `test_sources_distinguish_new_and_inherited` expected 114 source records, while the concurrently changing source register contained 127. An earlier run before that source-register change passed all 94 with one skip. The source-register change belongs to other work and was not reverted here.
