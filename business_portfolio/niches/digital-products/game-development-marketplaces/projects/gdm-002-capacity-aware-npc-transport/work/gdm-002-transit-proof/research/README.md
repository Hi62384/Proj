# FlowAI primitive comparison setup

The original `test_flowai_primitive.gd` is a preliminary three-node pathfinding check, not the requested same-scenario passenger comparison. It was run against FlowAI commit `f0fca85e3222cc2ad42d9668eb22006b149e1d71` in an isolated, ignored Godot project. FlowAI is MIT licensed; the external source and its license remain in that temporary project and are not part of this proof. To reproduce, obtain that exact revision from https://github.com/a6xdev/FlowAI, place it under `addons/FlowAI` in a separate Godot project, copy this test into that project, run a headless editor import to register global classes, and run `godot --headless --path <project> --script res://test_flowai_primitive.gd`. The observed run found three path points but logged resource-leak warnings at shutdown. This establishes neither performance nor passenger coordination behavior.

`test_native_fifo_baseline.gd` runs in the proof project. It builds three native navigation regions connected by two links and runs an independently written, fixed FIFO timetable alongside that route check. It compares the resulting 80-event happy-path trace with `scheduled_fixture.gd` and checks continuation from a trusted Variant disk save. Navigation pathfinding is only checked once; the script does not drive 20 NavigationAgents or model asynchronous boarding, disruption or physical recovery.

For `test_flow_fifo.gd`, copy it and `scheduled_fixture.gd` to the root of the isolated FlowAI project described above. Its scheduling code is the same minimal FIFO code as the native baseline, replacing only the graph setup with a FlowAI pathnode graph. It checks the same 80-event trace and trusted disk restore. The run exited 0 but emitted ObjectDB and resource-leak warnings. This is a bounded common-scheduler comparison, not an independently timed FlowAI integration. No development-time measurements were recorded. Test the same delayed-callback, missed-boarding, cancellation and restoration scenarios before drawing a differentiation decision.

`test_negative_comparison.gd` compares the ledger fixture to the separately written `diy_callback_baseline.gd` on one fixed trace: cancellation, duplicate cancellation, canceled and duplicate boarding callbacks, one missed departure, an old token on the next departure, trusted disk save/restore during boarding, and continuation to 19 arrivals. Both produced the same 78-event trace. The initial DIY restore accepted a snapshot that assigned the same passenger to two vehicles; the ledger restore rejected it. `diy_validated_baseline.gd` adds ownership, capacity and basic state checks; `test_validated_comparison.gd` then passes the same trace and rejects that corrupt snapshot too. These tests do not exercise navigation movement, vehicle breakdown, inaccessible stops, dynamic route planning, physical recovery or arbitrary controllers. The DIY and ledger implementations were written by the same AI in the same environment using the same known scenario; this is not a blind or independent developer study.

On this workstation, the wall-clock interval from beginning the initial DIY implementation to its first passing test was approximately 49 seconds, and the later validation addition and test approximately 24 seconds. These are observed intervals for this AI-assisted local experiment, not measured human engineering time or a fair end-to-end integration comparison: the ledger fixture was built in earlier turns without equivalent timing, and neither baseline integrates a real movement controller. The initial DIY file has 83 nonblank, non-comment lines; the validated version has 114. The ledger schedule and separate ledger have 110 and 74 respectively, but their scope differs and line count is not an effort or quality measure.

Decision: the required differentiation gate has **not passed**. The simple alternative now covers several selected lifecycle cases as well as the happy path, and no lower integration effort for the candidate has been measured. Do not package or market this as an advantage on this evidence. Continue only with the missing same-input disruption and real-controller integration evaluation needed to make the gate decision; no paid release or commercial action is authorized by this result.

The `test_navigation_integration.gd` and `test_navigation_midride.gd` scripts exercise one actual Godot `CharacterBody3D` and `NavigationAgent3D` against both the ledger and validated DIY implementations on identical navigation maps. The first uses two link callbacks to drive a fixed two-leg journey; the second interrupts the first leg, retains the stranded passenger's seat, moves the body back to a designated safe position and acknowledges rescue. Both compare event traces. The body moves directly across links without vehicle physics, ground collision, obstacles or a second controller style; schedule ticks are driven by the test. This is not an integration-cost benchmark.

The original `test_flow_controller.gd` and `test_flow_midride.gd` use a FlowAI agent and a `CharacterBody3D` in the isolated project. Copy the scripts, `callback_schedule.gd`, `transit.gd`, and `research/diy_validated_baseline.gd` into the corresponding paths of the isolated FlowAI project before running them. FlowAI's moving body uses position thresholds to trigger the fixed timetable, and returns directly to the safe point on interruption. These scripts use one passenger and have the same physics and timing limits as the native tests. FlowAI logged its known exit resource warnings. The first happy-path run also failed its target-distance assertion with the default path distance; setting `path_desired_distance` to 0.15 produced the documented passing rerun.

`test_navigation_twenty.gd` runs 20 CharacterBody3D/NavigationAgent3D pairs through the two fixed services, checking that each body physically reaches its next stop before the timetable processes its arrival. It checks 49 ticks, 20 completed passengers and identical 80-event traces for the two implementations. `test_navigation_twenty_interrupt.gd` checks that three boarded bodies have moved between stops, invokes the fixed disruption, returns them directly to a known safe point and acknowledges their rescue. The two implementations produce the same 26-event trace. There are no collision obstacles, platform physics, autonomous service planning or navigation-based recovery in these tests.

`test_flow_twenty.gd` and `test_flow_twenty_interrupt.gd` run the corresponding body tests with FlowAI in the isolated project. Copy those scripts plus the ledger and DIY files listed above into that project; third-party source stays separate. Both passed with the same tick and event counts and FlowAI's existing exit resource warnings. A physics-frame-driven elapsed time printed by the happy-path tests is a run duration, not a setup-time or integration-effort measurement.

`test_navigation_twenty_restore.gd` and `test_flow_twenty_restore.gd` add a disk checkpoint while selected bodies are physically between the second pair of stops. They store each model plus body position, target and moving flag, destroy and recreate the 20 bodies and navigation agents, then continue and compare each trace with the original unrestored 80-event reference. The FlowAI version also requires `scheduled_fixture.gd` in the isolated project root. This is a test-specific trusted Variant snapshot with a fixed graph and no collision, dynamic obstacles, physical vehicles or external game state; it is not a product save API. The first draft saved too late and failed its in-motion check; later runs moved the checkpoint earlier and asserted the position was between stops.
