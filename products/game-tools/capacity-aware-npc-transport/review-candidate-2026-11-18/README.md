# Transit coordinator â€” local development build

This is an unpublished Godot 4 prototype for scheduled, capacity-limited NPC journeys. It is not ready for a production release. The local example uses 20 synthetic passengers, two visual platforms, a transfer, a backup service, disruption recovery, and a trusted local save. The coordinator manages schedules and seat claims; the game remains responsible for navigation, physical movement, collision, vehicle positioning, and safely completing or rejecting movement requests.

## Try the example

Open this directory as a Godot 4 project and run the main scene. The buttons pause, change the fast connection between ticks, and save or load a local example snapshot. Disabling the service may request recovery for passengers on that service. Empty platform return motion is illustrative and supplied by the example. The example is not a physics or navigation integration test. The current automated runs use Godot 4.5.1; compatibility with other versions is not established.

## Integrate

See `API.md` for the current configuration, clock, event and persistence contracts.

Add `addons/transit_coordinator/transit_coordinator.gd` as a Node and connect its `transit_event` signal before configuring it. Supply a graph dictionary containing `revision`, `tick_unit: "simulation_tick"`, stop IDs, vehicles with integer capacities, and recurring directed services with integer `period`, `offset` and `duration` plus an `enabled` boolean. See `demo/transit_demo.gd` for a complete configuration. IDs must use ASCII letters, digits, underscore, dot or hyphen. Services using the same vehicle must not overlap. The coordinator does not model the vehicle's physical position or its empty return journey; the game must arrange those movements in the available time.

Call `request_journey(agent, origin, destination)`. On the owning thread, advance each logical tick with `begin_tick()`, then `open_boarding()`, then `finish_tick()`. Allow enough time between these calls for the game to complete and acknowledge physical alighting and boarding. For `boarding_requested` and `alighting_requested`, move the agent and call the matching acknowledgment using the event's agent, vehicle, token and event ID. For `recovery_requested`, move the agent to one of `details.safe_stops` and acknowledge that stop; if none is safe, keep the seat occupied until the game can recover the passenger. Do not acknowledge movement that did not actually complete. Events can be emitted synchronously, and acknowledgments can emit more events; do not change tick phase or save from inside a signal callback. Failed or stale acknowledgments return false.

An optional `navigation_adapter.gd` provides a small `CharacterBody3D`/`NavigationAgent3D` movement bridge. Configure it with the coordinator, register each body and navigation agent, then pass each movement request to `move_for_request()` with a game-chosen target and an arrival predicate. The predicate must verify that the body is actually on the intended vehicle or safely at the intended stop; a nearby coordinate alone is not enough. The adapter acknowledges only when both the distance and predicate pass. It rejects stale requests before starting and stops an active movement if that request expires or is superseded. It reports timeouts, supersession and rejected acknowledgments through `movement_failed`; the game must decide how to recover. Cancelling adapter movement does not cancel a journey or release a seat. If a game has confirmed that an NPC has been destroyed, it can explicitly call `remove_destroyed_agent(id)` to release that agent’s claim or seat and cancel the journey; use safe recovery instead while a physical passenger still exists. It assumes horizontal X/Z movement and a fixed gravity, and does not provide vehicle control, path creation, obstacle policy, body lifecycle handling, or persistence of in-flight adapter movements. Treat it as an integration starting point and adjust it for the game. See `tests/test_navigation_adapter.gd` for a small example.

Change service or stop availability between ticks. Inspect `journey(id)` and `diagnose(id)` for state and reason, or `inspect_vehicle(id)` for a copied FIFO queue and seat ledger. An optional `debug_overlay.gd` CanvasLayer displays vehicle queue previews, occupancy and one selected agent’s reason; set its coordinator path, vehicle IDs and agent ID. It is a runtime diagnostic. For an editor-only stop marker, enable the Transit Coordinator Tools plugin in Project Settings, attach `editor/stop_marker.gd` to a Node3D and set its stop ID. The gizmo is an authoring aid; it does not create or modify the timetable graph. `save_snapshot()` and `restore_snapshot(config, snapshot)` require the same graph and are intended for trusted local data. The current snapshot format is version 5. Compatible version-4 snapshots are upgraded on restore; versions 1–3 have no migration. After restore, `pending_request(agent)` reconstructs an outstanding boarding, alighting or recovery request with its original ID and token (its `tick` is the current tick). Restoring can also deliver events that were pending in the snapshot, so deduplicate work by request ID. Restore the game's body and vehicle state, choose a safe target, and explicitly restart the adapter movement; the adapter does not serialize game objects or movement progress. Store snapshots using the game's own persistence and validation policy; do not deserialize untrusted input as executable objects. The included demo save is only an example.

## Current limits

- Routing chooses an earliest arrival from the timetable; it does not predict or reserve future capacity. Equal-arrival choices use a deterministic local ordering, not a globally optimized fairness policy.
- There is no walking graph, automatic pathfinding, physics, multiplayer synchronization, editor UI, or automatic vehicle positioning. Vehicle schedule validation does not establish physical feasibility.
- Onboard cancellation requests a safe recovery and retains the seat until the game acknowledges that recovery; during the boarding-confirmed phase it must be retried after departure. Movement failures need an adapter-specific timeout or safe recovery policy.
- Scale, long-term fairness, starvation, performance in real games, compatibility across engine versions, migration, adversarial saves and real controller integrations are not yet established.
- Existing comparisons do not establish a reliability or integration-effort advantage. Do not make comparative marketing claims based on these tests.

## Local verification

Run each `tests/test_*.gd` with Godot's `--headless --path <this directory> --script res://tests/<file>`. For an isolated copy/remove/reinstall smoke check, run `python tools/verify_install.py <path-to-godot-console>`. For a headless editor plugin/marker smoke check, run `python tools/verify_editor.py <path-to-godot-console>`. The tests cover graph and ledger contracts, journey lifecycle, disruption, edge cases, stop closure, node integration, demo replay, a demo disruption, one explicit CharacterBody3D carry experiment without collision shapes, collision-based platform scenes with one and four passengers, navigation boarding on a flat mesh, a blocked physical exit and a safe-stop recovery. Review Godot output for script errors as well as the exit status. A sandbox root-certificate-store warning was observed even on passing offline tests.
