# GDM-001: real-game candidate and independent comparison protocol

## Candidate and verified scope

[NightRealm](https://github.com/T-qa/NightRealm) is a public Unity RPG whose repository describes a playable game with JSON persistence. The local research checkout is `products/game-tools/historical-save-regression-lab/experiments/NightRealm-external`, pinned to commit [`9fd092d0b235c725cf281e1da5d97da51e5ccd31`](https://github.com/T-qa/NightRealm/tree/9fd092d0b235c725cf281e1da5d97da51e5ccd31). Its [repository license](https://github.com/T-qa/NightRealm/blob/9fd092d0b235c725cf281e1da5d97da51e5ccd31/LICENSE) is MIT; independently verify included third-party assets and dependencies before redistribution. Its project specifies Unity 6000.3.10f1, while 6000.6.9f1 is installed; successful upgrade and dependencies are unverified. The checkout has not been opened or run in Unity, and no gameplay or historical compatibility is claimed.

Static inspection shows `FileNameData.SavePath` uses `Application.persistentDataPath`, while `SaveLoadHandler` reads and writes under a selected user directory. `GameManager` loads and saves a separate GameStatus file and invokes save/load around scene changes. `PlayerLevelSystem` restores player level, XP and capacity from a PlayerLevel file and updates gameplay stats; inventory, equipment and other systems use additional files and wrapped serialized data. The current GDM prototype's one-file fixture and in-process adapter do not establish isolation for that workflow. The checked-in A* Editor extension has an automatic update-check initializer and writes editor preferences; its network-send lines are commented out in this revision. Third-party Editor code as a whole has not been security reviewed. Do not use existing player data or run this game through the unconfined prototype.

A noteworthy static observation: `PlayerLevelSystem.SaveToFile` assigns `currentXp = CurrentLevel` rather than `CurrentXp`. This is a source-level candidate defect, not a reproduced gameplay regression or a GDM result. A future controlled round-trip could set unequal values, save and restore, and inspect gameplay state. It must not modify or report an upstream defect without authorization.

## Feasibility prerequisites

1. Review project and embedded asset licenses and auto-executing Editor code. Work in a disposable copy with no real profiles or customer data. Establish a controlled, independently verified scratch persistent-data root for *all* game files and child processes, with network and hard timeout controls. The existing unrestricted Editor runner and the standalone synthetic canary do not supply that guarantee for this game.
2. Pin source commit, Unity and packages; capture all temporary fixture files and hashes before and after each run. Identify actual game-produced historical saves and their versions. No such saves are present in the inspected checkout; generated current-version saves are useful for round-trip tests but must not be labeled historical.
3. Define a restore completion signal tied to the real game lifecycle. Exercise scene startup and post-load gameplay objects, including inventory/equipment and level state, not just JSON deserialization. Test a clean fixture, deliberately injected regressions, timeouts and missing/corrupt files. Record only non-sensitive identifiers and no save contents by default.
4. Bind the experimental harness to the reviewed game and adapter and label results as claims of that trusted integration. No worker-side marker authenticates honest restoration. Fail closed for missing, malformed or untrusted output. Do not infer broad containment from a few canaries.

## Independent setup and maintenance comparison — protocol, not results

No independent developer is currently available. When one is available, use a developer who did not author either integration, disclose prior exposure, and give both paths the same pinned game, editor, fixtures, expected state, fault injections and documentation. Use separate fresh workspaces, randomize or counterbalance order across participants if feasible, and record order and prior experience. Never claim blinding if it did not occur.

Measure wall-clock and active effort separately for installation, creating/running passing tests, diagnosing the same two pre-defined faults, and a pre-specified maintenance change (for example adding one persisted gameplay assertion). Include time spent learning, configuring fixture isolation, writing adapters/assertions, running tests, troubleshooting and verifying reports. Retain timestamps, commands, diffs and redacted CI reports with participant consent. Record failures, abandoned attempts, assistance and exclusions; do not replace missing timings with guesses. Check source hashes and verify that neither path touched real saves. Independently assess whether safety, scope and reporting are equivalent before comparing time.

A real-workflow advantage is not established by this protocol or the same-author synthetic timings. The current in-Editor runner already fails the isolation requirement, so defer release regardless of timing until that gate is met. No outreach, compensation, account creation or external scheduling is authorized by this research.


## Multi-file staging preparation

An experimental Python helper stages a bounded map of named synthetic files after checking SHA-256 hashes; two tests cover copied-byte independence, cleanup and rejection of bad names and hashes. It is not connected to NightRealm or Unity, does not redirect the game's persistent-data root, and is not a sandbox. It does not establish race-free filesystem access or comprehensive Windows reparse-point handling. Source: `experiments/appcontainer-canary/multifile_stage.py`.


## Contained NightRealm Editor startup probe

The supervisor copied the pinned checkout's Assets, Packages and ProjectSettings into a fresh AppContainer profile. It changed the copy's `FileNameData.SavePath` to a newly created profile-local folder and added a temporary Editor entry point that would write and read synthetic `GameStatus` and `PlayerLevel` files through the game's generic `SaveLoadHandler`. The original checkout was not modified. The copied project was launched in the installed Unity 6000.6.9f1 Editor with no capability SIDs, handle inheritance disabled, a verified AppContainer token, a Job Object and a 120-second deadline.

The Editor exited 1 before the entry point ran. The log reported that Unity Package Manager could not connect to its local IPC server; it also recorded refused licensing IPC and Windows assertions. There was no completion marker and the disposable save root was empty. The job reported 10 associated processes and zero active processes after termination; the temporary AppContainer profile deletion succeeded and the profile directory was absent on inspection. Structured evidence is `experiments/nightrealm-appcontainer-observation.json`; source is `experiments/appcontainer-canary/nightrealm_unity_probe.py`. The game did not execute the save round-trip or gameplay restoration, so the patched root was not verified at runtime and no safe real-game environment is established. This does not prove every restricted Unity configuration will fail. No broad ACL or system security changes were made. The independent comparison remains blocked by the absence of an independent developer.


## Standalone NightRealm save-handler probe

A separate minimal Unity 6000.6.9f1 project built a Windows player with a byte-identical copy of NightRealm's `SaveLoadHandler.cs` (SHA-256 `c0ddcd6ed7d6a3b72fb71ec2f5559894f4b2e0d5ea9d9127b4468fd157c5be30`), a copy of `FileNameData.cs` whose save root derives from a supervisor-provided scratch path, synthetic data classes, and stubs for the unused wrapped-object overloads. The NightRealm MIT notice is retained in the probe project. The original game checkout remains unchanged.

An unrestricted control and a no-capability AppContainer run each exited 0. Each generated synthetic GameStatus and PlayerLevel input files in its private scratch directory, loaded them using the generic handler, and wrote two output files with the same handler. Before cleanup the supervisor independently parsed all four files, checked the values and recorded hashes; the two input/output hash pairs matched. Both copied unrelated control fixtures were unchanged. The unrestricted outside canary was written; the restricted canary was absent and the worker reported `DirectoryNotFoundException`. The restricted token was AppContainer, job accounting ended at zero active processes, and profile deletion succeeded. Observations: `experiments/nightrealm-savecode-build-v1/nightrealm-savecode-observations.json`.

These are worker-generated synthetic files, not historical saves. The player contains neither NightRealm gameplay components nor its scene or wrapped inventory implementation. It does not test the prior XP-save issue, actual game integration, a trustworthy hostile-worker report, or comprehensive filesystem and network confinement. A nonexistent outside canary and directory error do not prove all outside access is blocked. The Editor needed to build this small reviewed probe ran outside the restricted profile; the original full-game Editor still failed its restricted Package Manager startup. The result establishes a narrow save-code feasibility step only.


## Original level component in a restricted player

A minimal standalone Windows Unity player included the exact upstream `PlayerLevelSystem.cs` from the pinned revision (SHA-256 `f3e6ac54b91f44e5485487dec04f104a57718e40a7aeb44474c577d397a43569`), the original generic save handler and a patched copy of its path helper. The player instantiated the real component, but used test substitutes for its fighter/stats, event, audio and pooling dependencies; it did not include NightRealm's scenes or inventory. The trusted harness used a synthetic profile-local GameStatus and PlayerLevel file with level 2, XP 7 and capacity 100.

An AppContainer initial-load run observed the component restore XP 7 and exited 0. A separate restricted save-and-reload run observed XP 2 and exited 1 with `player.currentXp`; an unrestricted control produced the same result. Before deleting each temporary profile, the supervisor independently parsed the saved before/after PlayerLevel files and verified the input XP 7 and output XP 2. Restricted tokens were confirmed, outside canaries were absent, job accounting reached zero active processes and both profiles were deleted. The unrestricted canary was created. Raw observations are `experiments/nightrealm-level-build-v1/nightrealm-level-observations.json`.

This reproduces the earlier source-level XP issue in a component harness with synthetic data: `SaveToFile` stores level as XP. It is not a full-game or historical-save test and does not establish the market value of the prototype. The outside-write diagnostic was `DirectoryNotFoundException`, which does not establish comprehensive isolation. The worker still supplies its own state claims; file inspection verifies the emitted bytes, not the honesty of hostile code. No upstream game files were modified and no issue was sent.
