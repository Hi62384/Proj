# Experimental Windows isolation probe

This is a feasibility result, not an enabled Portfolio Manager backend. The owner requested a Windows replacement for both background workers and project tests, without relying on WSL. The existing WSL backend and its restrictions remain unchanged.

On Windows 10 Home, `python -m portfolio_manager.tests.live_windows_isolation` creates a disposable Windows AppContainer profile, runs synthetic probes, then removes that profile. It copies an existing Python runtime and the selected Codex executable into the disposable profile, and contacts `https://example.com/` only to compare a network-enabled container with the host. It uses no account credentials or project files. The command is opt-in and requires access to create a per-user AppContainer profile. It currently exits unsuccessfully because the complete worker check is blocked.

Observed on November 12, 2026:

- A Windows process and a copied Python interpreter started inside the AppContainer. A fictional Python test passed and an intentionally failing test failed.
- The container read a synthetic file inside its own profile but was denied a separate synthetic file outside it. A local HTTP listener reachable by the host was unreachable from a container with no network capability; a separate process with the Internet Client capability reached a public test site. These are limited probes, not a complete security audit.
- A later probe verified the test process had an AppContainer token. A first attempt to protect a fixture using a deny entry failed: the fixture actually changed. A revised disposable-folder ACL, created with explicit read-only container access and full owner/System access before the fixture was created, allowed reading and blocked both writing and deleting that fixture. Actual passing and failing Python test files then ran from that read-only folder and were classified correctly. The probe verifies file contents and existence rather than relying on shell exit codes. This remains experimental and is not integrated as a verifier.
- The Windows Codex executable started for `--version`, but its app-server could not initialize with an explicitly configured private home: Windows denied the path canonicalization. With that variable unset, the app-server could not find its home directory. Both the installed `0.162.1` executable and an integrity-verified, test-only official `0.167.2` executable had the same result. The latter was not installed and its temporary download was removed.
- This matches the behavior reported in [Codex issue 45871](https://github.com/openai/codex/issues/45871). A temporary unused drive mapping and a separate disposable staging folder did not resolve it; both were removed. The probe did not modify Windows system permissions or relax the existing Codex worker profile to work around it.
- A further test supplied the same private home using a Windows volume-GUID path instead of a drive-letter path. The app-server still reported access denied while canonicalizing that home. The standard drive-letter and unset-home cases were rechecked and also failed. The isolation, read-only-file, Python test, and network probes passed on that run, but the complete worker did not start.

Before an AppContainer backend can replace WSL, the Codex app-server must initialize in the container without weakening the filesystem restrictions. Its protocol, authentication, worker cancellation, resource limits, recovery, output integrity, network policy, per-task cleanup, and Python/JavaScript verification would then need end-to-end tests. In particular, the limited probes above do not prove WSL-equivalent isolation or that production project tests can safely be run there. Do not select this experiment as a production fallback.

## Restricted-token alternative

An additional opt-in experiment, `python -m portfolio_manager.tests.live_windows_restricted_token`, creates a disposable restricted Windows token and applies an access entry only to its own temporary fixture. It does not create accounts, install a service, or change firewall rules. A private, non-visible desktop in the existing window station was also tested without changing the existing desktop's permissions. The narrow configuration could create processes but a Windows command, a minimal kernel-only executable, and the copied Codex executable all failed to initialize (`0xC0000142`); therefore its file-access checks did not run. Adding the existing logon-session identity did not resolve this. This is not a working backend.

The experimental restricting identities include the built-in Users group to make Windows system files readable. That group can also have access to unrelated files, so even a successful launch would not by itself establish the existing root-deny guarantee. A separate `--diagnose-user-sid` comparison deliberately used a broader temporary token: it started, but read a deliberately shared outside fixture, and the probe rejected it. It is not eligible as a backend. Any future alternative must demonstrate denial of unrelated, broadly shared files as well as its permitted files, and must separately restrict network access and process resources. Windows job objects can help limit resources, but Microsoft documents that process security limits need separate enforcement; a job object alone is not a replacement for the current sandbox.

An additional read-only access check found that the restricted token could read window-station attributes, use global atoms, and enumerate the station, yet both the command and Codex still failed with `0xC0000142`. Those particular permissions therefore do not explain the failure; the check does not establish that every resource needed during initialization is accessible. No window-station permissions were changed.

Codex also recognizes an external-sandbox mode, but its own implementation selects no built-in sandbox for that mode. It assumes an independent outer boundary already exists, so selecting it alone would not resolve the Windows isolation problem or justify enabling the worker.

## Startup source review

The [Codex home-directory implementation](https://github.com/openai/codex/blob/main/codex-rs/utils/home-dir/src/lib.rs) explicitly checks that `CODEX_HOME` is a directory and then canonicalizes it. In the disposable AppContainer, the existing directory is accessible but this canonicalization fails; leaving `CODEX_HOME` unset fails at Windows profile-home discovery instead. The current upstream issue also describes separately affected working-directory resolution. Thus fixing only the home variable does not establish that the app-server, thread setup, or project execution can complete.

The upstream issue suggests lexical path absolutization as a possible implementation change. It is not interchangeable with resolving filesystem links: a junction or symlink can make a lexically contained path resolve elsewhere. A candidate must preserve the security checks at each affected call site, including reparse-point handling and race resistance; simply accepting a lexical path is not an approved workaround. No patched Codex binary or upstream fix has been verified here. The next concrete dependency is a security-reviewed upstream fix or a locally built and reviewed candidate that resolves both home and working-directory initialization, followed by disposable end-to-end boundary and lifecycle tests. The local Rust tools are present, but the necessary reviewed candidate and its build have not been established; the existing installed executable and live worker configuration remain unchanged.
