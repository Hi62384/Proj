# GDM-003 integrated feasibility spike — 2026-11-18

The prior decision to pause implementation was premature. The project plan calls for a comparison against a minimal engine-aware verifier. The previous DIY helper consumed Dependencies output and understood only the owned fixture; those observations alone did not prove it equivalent to an integrated tool. The prior record is preserved with this correction. The go/kill decision is **open**, not a claim of competitive or commercial validation.

## Observed work

`products/game-tools/native-dependency-verifier/spike/` now contains a local feasibility probe, not a releasable product. A .NET 8 `PEReader`-based CLI reads one PE without loading it, bounds its input and import directories, reports machine, ordinary import names and RVA-form delay-import names, and explicitly lists dynamic loads and loader resolution as unknown. Unsupported delay-import address forms are rejected. An initial build failed because the sandbox could not reach NuGet and the default Windows apphost pack was unavailable; building with `UseAppHost=false`, an empty temporary package source configuration and local SDK 8.0.302 succeeded with zero warnings and errors. No third-party package was restored.

A separate Python integration experiment invokes that probe, reads the exact owned fixture's limited descriptor syntax, traverses package-root fixture DLLs, and emits deterministic JSON with import chains, the checked descriptor field, dependency destination and confidence limits. It is deliberately restricted to trusted owned fixtures and an observed flat Godot export; it is not an arbitrary descriptor parser, complete PE scanner, safe untrusted-input tool, or production CLI. No Dependencies output is used by this experiment.

Against the previously generated Godot 4.7.2 fixtures, the integration experiment reported the missing root DLL, missing transitive leaf, omitted dependency declaration, nested destination, misplaced leaf, x86 extension and missing extension. The clean fixture produced no findings but returned exit 3 because runtime and loader checks remain unknown; cases with a finding returned 1. It did not consult the host PATH and therefore continued to report the package-root absence in the documented outside-package resolution example, while explicitly leaving host behavior unknown. It does not establish that absence at the package root means the Windows loader must fail.

Eight PE-probe tests passed: x64/x86 imports and input hashes, an MSVC-built delay-load import, invalid delay descriptor address forms and RVAs, the dynamic-load blind spot, truncated and deliberately invalid-name-RVA binaries, invalid import-directory sizes, an oversized input, and 14 deterministic header mutations checked for controlled exits. Twelve integration tests cover the original fixture scenarios, embedded PCK, the host-resolution case, a missing delay-loaded DLL, feature-selection cases, a custom-feature rejection, distinct/identical basename collisions, Windows junction and hardlink rejection, path traversal, an entry limit, and an optional per-PE handle mode, including package input hashes. The delay-loaded DLL is reported as runtime-dependent unknown, not a confirmed failure. The scanner's path checks are not race-resistant and do not make the spike safe for hostile files. These checks are limited to the named fixtures and are not comprehensive parser security, clean-host, performance, general delay-import, general engine-version, or commercial acceptance tests. The fixture-specific script and Dependencies remain capable free alternatives; the spike has not established a general product advantage or measured diagnosis time.

Three additional Godot 4.7.2 exports exposed a distinction between the two descriptor sections. A valid specific library entry won over a missing generic entry even when the generic entry came first; reversing which path was missing caused export failure. A first matching generic dependency map omitted `leaf.dll` even though a later, more specific map listed it; the export completed without the DLL and the owned game reported error 126. The [4.7.2 loader source](https://github.com/godotengine/godot/blob/4.7.2-stable/core/extension/gdextension_library_loader.cpp) selects a matching library with the most tags and stops at the first matching dependency map. The experimental parser now models this distinction only for its explicit fixed feature set, rejects unknown feature tags, and correctly flags the missing source library and the omitted leaf in these cases. This does not establish behavior for arbitrary custom features, other Godot versions, or all descriptor syntax.

A separate owned project contained two selected extension libraries at different source paths but with the same basename. One was made byte-distinct using a harmless appended test marker. Godot's export returned 0 and staged one `extension.dll`; its SHA-256 matched the second source file rather than the first. The export log contained no collision warning, although it did contain the previously noted certificate-store error. The experiment does not establish which file wins generally or that this particular marker changes runtime behavior. The spike now compares selected source-library basenames and hashes for its trusted, fixed-layout test projects, reporting the two declarations and different hashes. A control with byte-identical files did not produce a content-collision finding. This gives a concrete engine-context example not exposed by inspecting the one surviving DLL alone; it remains to compare the effort and generality of a small free-tool script fairly before a go/kill decision.

A separate small DIY script, `fixture/collision_challenge.py`, also identified the differing source hashes and returned 1 for this collision project and 0 for the clean single-extension project. Like the first DIY helper, it assumes the controlled fixture's exact release key and is not a general Godot parser. The collision therefore shows a concrete integration opportunity, not proof that the proposed product is meaningfully better than a small script. The scripts' authoring and diagnosis time were not measured.

`fixture/build_owned.py` now rebuilds the owned DLLs and export variants in a fresh caller-selected directory from separately supplied tools. A full rebuild using the stated editor, template, header and MSVC installations completed, and all six PE tests and seven integration tests passed against those newly generated files. The clean exported game reported the extension loaded; the regenerated omitted, nested, and first-matching-dependency-map variants reported it not loaded and error 126. The builder rejected an attempt to reuse its output directory. An initial builder attempt failed because of Windows command quoting; that attempt did not produce a valid build and the corrected builder was rerun in a separate new directory. The editor version is checked; supplied template and header hashes are not verified by the builder. Generated binaries and tools remain outside the public results.

On the regenerated clean, omitted, nested and first-matching-map cases, the standalone spike reported the respective clean-but-unknown state or the expected fixture chain and checked map. The first DIY helper initially misidentified the first-matching-map case because it read the later `windows.x86_64` entry; after it was extended to recognize the two tested keys in order, it reported the relevant `windows` map and absent leaf. The revised helper remains narrowly fixture-specific, not an independent general parser. Dependencies' chain commands took approximately 14–16 seconds each on this host, while individual spike invocations took approximately 0.5–0.7 seconds and the helper consuming already-generated JSON took approximately 0.08–0.10 seconds. These are single, non-equivalent executions: Dependencies traversed host/system chains that the spike did not, and the numbers exclude setup, authoring and human diagnosis. They do not establish a general speed or commercial advantage.

As an additional read-only check on this host, the probe's ordinary and delay-import name lists agreed with `dumpbin /imports` for four installed Windows system DLLs. The paired counts were 96/2 (`kernel32`), 42/6 (`user32`), 22/0 (`version`) and 31/15 (`winmm`). These are observations for the installed files, not a portable compatibility matrix or license to redistribute them.

An owned export with the PCK embedded into the executable also returned 0 and loaded the extension; the native DLLs remained beside the executable in this one case. The fixture builder and integration tests now include this variant. The spike still receives the source descriptor explicitly and does not inspect the embedded PCK or prove general embedded-export behavior.

After adding the embedded variant and editor-version check, the complete builder was run again in another fresh directory. Both probe and integration suites passed against that output. The later malformed-size test was also run against it. No generated fixture or third-party binary was added to the public result.

## Next action

Extend the comparison only within the project's bounded feasibility gate: test actual Godot staging rules beyond the fixed fixture, broaden malformed-file and delay-import handling, and compare the integrated output and effort against the same free-tool workflow. A generic finding must not be inferred from the fixture-only mapping. Only after a meaningful advantage and the project's stated cases are demonstrated should the larger product/release tasks proceed. No sale, external publication, customer contact or spending occurred.
