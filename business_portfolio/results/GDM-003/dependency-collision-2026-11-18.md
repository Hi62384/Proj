# GDM-003 dependency collision follow-up — 2026-11-18

The earlier conditional pause was based on a bounded set of fixtures, not proof of equivalence. This follow-up tested a distinct case before relying on that decision: two owned Godot extensions with different library names each declare a different `root.dll` for the same output directory. The second `root.dll` was built from the owned `fixture.c`; it exports `fixture_value`, while the first extension imports `root_value` from `root.dll`.

On this Windows host with Godot 4.7.2, export returned 0. The exported root DLL's SHA-256 matched the second source and differed from the first; the owned game returned 0 but reported error 127, “The specified procedure could not be found,” and `GDM-003 loaded: false`. The export log contained the previously observed certificate-store error but no collision warning in this experiment. This establishes a runtime failure for these exact files and settings; it does not establish general overwrite order or imply that every same-name dependency collision fails.

Before this follow-up, the integrated fixture spike returned no finding and exit 3, and the library-only DIY collision script returned 0. That was an incomplete result, not evidence that the export was healthy. The spike was extended to compare selected staging declarations when their observed fixture destinations and basenames coincide. It then reported both manifest fields, source paths, hashes and the shared destination. Tests also checked that byte-identical source DLLs and different destinations were not called the same content collision. Later synthetic-metadata tests covered a collision between two other extensions and one between an extension library and a dependency; those two tests did not perform a Godot export. This remains a fixture-specific implementation and does not model arbitrary descriptors or all Godot paths and export modes.

Dependencies' `-chain` resolved `root.dll` by path, while its `-imports` output named `root_value` and `-exports` on the staged DLL listed `fixture_value`. A new small, fixture-specific script compares those JSON outputs and returned 1 for the staged mismatch and 0 for the matching owned source DLL. It deliberately treats ordinal imports, delayed imports and forwarded exports as unsupported; two local tests passed, including case-sensitive symbol matching. The separate DIY collision helper was also extended to compare the fixture's dependency source hashes and destinations; it reported the two conflicting `root.dll` sources and passed controls for identical content and different destinations. The free-tool workflow thus can diagnose this named-symbol example and identify the controlled source collision with additional commands and small helpers. No timing or general equivalence claim is made.

The owned fixture builder and integration tests were extended for the case. A fresh source rebuild reproduced the failure: the staged DLL again matched the second source, Godot logged error 127, and the owned game reported the extension was not loaded. Against that rebuilt matrix, eight PE tests, seventeen fixture integration tests and two named-symbol helper tests passed. The earlier pause remains a conditional business decision, not a finding that no useful differentiated product is possible. The new case exposes a real failure that name-only dependency resolution misses and a gap in both initial comparison scripts; its generality, safe handling and commercial significance still need proof. No customer input, spending, publication or sale occurred.

## Single-extension replacement and false-positive control

A further owned package replaced the single declared `root.dll` after export with the incompatible DLL. Godot reported error 127 and the extension did not load; the earlier spike returned no finding and exit 3. The fixture spike now reports the source and staged SHA-256 values when a uniquely declared fixture file differs from its root-staged counterpart. This is a byte-difference observation, not a conclusion that the difference caused a failure.

As a control, an owned clean extension DLL had a harmless test marker appended; the exported game still reported `loaded: true`, while the hashes differed. The spike labels that difference advisory and returns 3 when it is the only finding, preserving uncertainty rather than treating a legitimate transformation as a confirmed defect. On this same local Dependencies version, `-json -modules` returned exit 0 with a message that JSON was unsupported, rather than JSON; robust integrations must inspect the output, not infer success from exit status alone. The non-JSON module listing resolved the staged `root.dll` by name. These observations apply to the tested tool/version and fixtures only.

The updated source-driven builder was subsequently run in a fresh directory. Both the successful benign-transform run and the error-127 replaced-dependency run reproduced. Eight PE tests and nineteen fixture integration tests passed against the regenerated matrix; the latter included hash checks of both the source project and package before and after scanning. This does not establish immutability under concurrent hostile mutation or full loader correctness.
