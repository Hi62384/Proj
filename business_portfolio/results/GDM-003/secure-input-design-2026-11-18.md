# Candidate Windows input-safety design

This is a design and a limited experiment, not a claim that the current trusted-fixture spike is safe for hostile packages. The current Python checks observe paths with `lstat` and later open them by name; another process can change a directory or file between those operations. The default companion PE process reopens each file by pathname, which introduces another race; an optional experimental per-file handle mode does not protect the scanner's metadata or whole traversal. Case-folding, Windows name aliases, junctions, hard links, alternate data streams, non-NTFS filesystems and network shares also need explicit handling. Do not run the spike on untrusted customer packages.

## Small handle experiment

`spike/safe_open/` contains a .NET 8 Windows-only experiment. It resolves a drive-letter root to an NT device path, requests a no-reparse open and then opens validated single path components relative to held directory handles. It checks the opened object type, reparse attribute and file link count, holds handles with read sharing, and hashes the file through the final handle. An optional experimental mode then parses that same stream with the shared PE parser without reopening its path. It rejects other NT device types, network-style roots and several unsupported path forms. The trusted-fixture scanner can optionally call this probe for each PE; it still reads metadata by pathname and reacquires the package root for each file. This is not a release or a production security boundary.

Six tests passed on this host, reported as Windows 10 build 19045 on NTFS: an owned PE was hashed and parsed through the same opened stream; ordinary owned file and traversal cases; a hardlink; junctions used as the selected root and as a child; attempted rename/write while the file and parent handles were held; and 24 open attempts while a test thread repeatedly swapped an owned directory with a junction to an owned outside sentinel. At least one swap occurred; no successful open returned the outside sentinel hash. The initial test harness failed because a legitimate sharing violation delayed restoration of its own test directory; after adding a bounded restore retry, the suite passed. An initial probe attempt using the DOS-device `\\??\\` path failed with status `0xC000050B`; mapping to the observed hard-disk device path allowed the regular case to open. No external or customer files were modified.

These observations do not prove race freedom or behavior on other Windows versions, volume types, redirectors, pre-existing handles, object-manager changes, or adversarial filesystem drivers. The implementation uses native APIs and still needs review of documented user-mode flag compatibility and root acquisition. The scanner's optional handle mode produced the same fixture findings as its original mode for clean, missing, collision and delay cases, but enumeration and source metadata do not use retained verified handles. A stress test can miss races. The trusted-fixture Python path remains subject to the races described above.

## Candidate approach to validate

1. Define supported input roots and filesystem/version matrix first. Reject network paths, device paths, alternate data streams, ambiguous case-folded names, and unsupported volume types unless separately designed and tested. Obtain an authorized root directory handle without following reparse points; do not assume that checking a string or only its last path component establishes this.
2. Traverse using directory-relative opens tied to verified handles, not by reopening concatenated full pathnames. One possible Windows design uses `NtCreateFile` with `OBJECT_ATTRIBUTES.RootDirectory` and a no-reparse policy, opening one validated component at a time. Microsoft documents directory-relative naming for [`NtCreateFile`](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile) and describes `OBJ_DONT_REPARSE` in [`OBJECT_ATTRIBUTES`](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_object_attributes). Their compatibility and exact guarantees for the chosen user-mode flags, Windows versions and filesystems still require verification; do not infer a complete security guarantee merely from these descriptions.
3. Inspect the opened objects' attributes and identities by handle, reject unsupported types and links, and define share modes and lifetime rules. Keep the same verified file handle through parsing and hashing, or make a bounded private copy from that handle and parse that copy. The current subprocess/path interface must change. A handle opened with [`CreateFileW`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) and `FILE_FLAG_OPEN_REPARSE_POINT` can open the final reparse point itself, but that fact alone does not prove that intermediate path components were safe.
4. Bound file count, directory count and depth, per-file and aggregate bytes, descriptor length, import count and graph depth, elapsed time, and report size. Reject unsupported or changing inputs with an explicit incomplete status; don't turn an I/O or parsing failure into a clean result. Preserve input bytes and never load or execute scanned binaries. Verify output location independently so reports cannot overwrite inputs.
5. Review hardlink policy carefully: a link count check is useful for the owned fixture experiment, but it is not a complete identity, privacy or race defense. Test real NTFS names and aliases, inaccessible directories, duplicate basenames, concurrent renames/replacements, junctions at every component, files modified during scanning, sharing violations, PCK inputs, and symlinks. Include tests that prove the outside target is never opened, not merely that a warning appears. A stress test can find bugs but cannot by itself prove race freedom; review the object/handle invariants and Windows API contract as well.

The research above does not authorize a new filesystem driver, privilege elevation, remote scans, or changes to customer files. Treat any unsupported semantics as an incomplete result, and keep host/system and dynamic loader resolution as unknown until a supported, separately validated model exists.
