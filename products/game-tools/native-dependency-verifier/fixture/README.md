# Owned fixture inputs

`fixture.c` is a synthetic native DLL source. `fixture.gdextension` is a path-testing descriptor; the DLL is not a functioning Godot extension and must not be presented as an exportable example. For a local architecture check in an x64 MSVC developer prompt, run `cl /LD /TC fixture.c` followed by `dumpbin /headers fixture.dll`. The comparison still requires a real GDExtension and actual engine exports.

`root.c`, `middle.c`, and `leaf.c` form a separate owned static-import chain. In an empty build directory, from an x64 MSVC developer command prompt, substitute the absolute source directory for `<fixture>` and run:

```bat
cl /nologo /LD "<fixture>\leaf.c" /link /out:leaf.dll
cl /nologo /LD "<fixture>\middle.c" leaf.lib /link /out:middle.dll
cl /nologo /LD "<fixture>\root.c" middle.lib /link /out:root.dll
dumpbin /imports root.dll middle.dll
dumpbin /headers root.dll
```

In a separate empty directory and x86 developer prompt, build `leaf.c` with `cl /nologo /LD "<fixture>\leaf.c" /link /out:leaf-x86.dll` and inspect its headers with `dumpbin`. Keep x86 and x64 build outputs separate: both compilers produce `leaf.lib`. For controlled missing-import variants, copy only the desired DLLs into a new package directory; do not modify the clean build. These DLLs are PE test inputs, not GDExtensions. The x64 chain was later loaded and called by the owned Godot export described below; the x86 DLL was not executed.

## Godot export experiment

To rebuild the fixture matrix from source, run `python build_owned.py --godot <Godot-4.7.2-console.exe> --template <matching-windows-release-x86_64.exe> --header <gdextension_interface.h> --vcvars64 <vcvars64.bat> --vcvars32 <vcvars32.bat> --output <new-directory>`. Supply the separately obtained Godot 4.4 interface header and matching Godot 4.7.2 Windows release template. The script checks the editor version and refuses to reuse an existing output directory; it does not verify the supplied template or header hashes. It compiles owned source, imports and exports disposable project copies, creates the negative variants, and records engine logs. Expect significant disk usage from multiple executable copies. It performs no downloads, does not publish anything, and leaves partial output in the chosen new directory on failure. MSVC command paths containing cmd.exe metacharacters or non-ASCII characters are unsupported. Verify downloaded tools and their licenses separately.

Add `--debug-template <matching-windows-debug-x86_64.exe>` to also build the optional debug export and missing-leaf copy. `python test_debug_diagnostics.py <experiment-root>` runs those owned binaries on Windows and compares a system-only `PATH` with one containing the clean fixture DLL. This is an environment-specific experiment, not a claim about all loader configurations.

The separate `godot/` project uses `extension.c` with the official Godot 4.4 C interface header (obtain it separately from `godotengine/godot` tag `4.4-stable`, `core/extension/gdextension_interface.h`). Build the x64 chain in a directory outside the project, then compile the extension using `cl /nologo /LD /I"<header-directory>" "<fixture>\godot\extension.c" root.lib /link /out:extension.dll`. Copy only the four DLLs into `godot/addons/fixture/bin/` in a disposable copy of the project, not build objects or import libraries. The entry point calls the chain when Godot initializes the owned extension.

For the observed test, use Godot 4.7.2 and its matching Windows x64 release export template, configure a Windows Desktop release preset with that custom template and a separate PCK, import the project, and export to an empty directory. The clean exported program prints `GDM-003 loaded: true` and quits. The clean source descriptor declares all three dependent DLLs. For the omission experiment, remove only the `leaf.dll` entry from the `[dependencies]` dictionary in a copy of the source project and export again. See the dated public checkpoint for observed commands, output, caveats and the scope of the comparison. Do not distribute the separately obtained editor, template, header or Dependencies without reviewing their respective licenses.

`diy_challenge.py` is a deliberately fixture-specific comparison aid, not a product parser: it expects this fixture's simple JSON-style dependency dictionary, including multiline entries and a trailing comma; it rejects semicolons and nested braces, the source `bin` directory, and Dependencies JSON generated with `-json -chain -depth 4`. Run `python diy_challenge.py <source-descriptor> <dependencies-json> [package-root]`. It accepts only the fixture's simple `res://addons/fixture/bin/<file>` and `./bin/<file>` dependency paths and rejects other forms. It reports unresolved names that also exist in that source `bin` and the destination in the one dictionary, if present. With a package root it also identifies matching fixture DLLs which Dependencies resolved outside that root as unknown. It returns 1 for a matching unresolved DLL, 3 for an outside-package resolution or repeated fixture path without such a finding, and 0 otherwise. It ignores other unresolved modules and cannot model general feature-tag selection, Windows loader rules, PCK contents, arbitrary manifests, architecture, or dynamically loaded libraries. Exit 0 is not a compatibility guarantee.

For a static-analysis blind spot, compile `dynamic.c` separately as a DLL and inspect its imports; its exported function calls `LoadLibraryW` with `optional-runtime.dll`. Do not call the function during this experiment. The imported Windows function is visible, but the runtime module name is not a static import.

`collision_challenge.py <owned-fixture-project>` is another deliberately narrow DIY comparison. It reads the fixture's exact `windows.release.x86_64` string entries and first dependency map matching either of its two tested keys, then reports distinct source hashes sharing a staging destination and basename. It does not implement general Godot feature matching or safe handling of untrusted projects, and does not prove that a basename collision changes runtime behavior. `test_collision_challenge.py` covers its owned synthetic controls.

The builder also creates `cycle-export`, whose owned `root.dll` and `middle.dll` import each other. **Do not execute or load these DLLs:** their bodies recurse indefinitely. The current builder omits the game executable and PCK from this data-only variant; older temporary fixture copies may still contain them. Inspect it only as data. The fixture spike reports the repeated static import chain as runtime-unknown; the Dependencies JSON helper also reports a repeated resolved fixture path and exits 3 if it has no missing-import finding. A cycle alone is not proof of runtime failure.

`custom_feature_challenge.py <descriptor> <package> [active-custom-feature ...]` is a separate small comparison for the owned feature-tag fixture. It selects among a restricted set of explicit tags and checks only for a root-staged file. It does not infer export-preset features or prove runtime loading; unknown tags are incomplete. `test_custom_feature_challenge.py <experiment-root>` exercises its controlled cases.

For the dependency-collision fixture, Dependencies can export separate JSON from `-json -imports <export>/extension.dll` and `-json -exports <export>/root.dll`. `symbol_challenge.py <imports.json> <exports.json> root.dll` compares the fixture's named imports with named exports. It explicitly rejects ordinal imports, delayed imports and forwarded exports; it is not a general loader or compatibility check. `test_symbol_challenge.py` exercises its bounded comparison.

For a reproducible command-timing comparison on four of the generated fixtures, run `python measure_workflows.py --fixtures <experiment-root> --dependencies <Dependencies.exe> --probe <PeProbe.dll> --output <new-directory>`. The output directory must not already exist. It stores Dependencies JSON and a summary locally; those files may contain host paths and are not appropriate for automatic public sharing. Timings exclude setup and human work, and the two tools inspect different scopes.
