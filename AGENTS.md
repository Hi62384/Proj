## ProjectBridge delivery modes — choose based on the request

- **Codex, IDE agents, local coding agents, and any agent working in a writable checkout:** **edit files directly** using the normal coding workflow, then test and report results. **Do NOT produce `ProjectBridge_patch.zip`** unless the user specifically requests it. The presence of these instructions does not mean ZIP delivery was requested.
- **Normal ChatGPT reading GitHub read-only, without a writable checkout:** for coding-change requests, **default to a ProjectBridge patch ZIP** unless the user requests another output. Read `PROJECTBRIDGE_PATCH_INSTRUCTIONS.md` **in full** before building a ZIP, then package only the relevant changes against the GitHub baseline.
- For all other tasks, use the tools and delivery format explicitly requested by the user. Never replace direct Codex edits, commits, or PRs with a ZIP without the user asking.
- Preserve project-specific build/optimization instructions elsewhere in `AGENTS.md`. Report tests honestly.

## Project execution persistence

- When the owner asks you to work on this project, continue autonomously through all remaining authorized tasks possible with available access and resources. Do not stop merely because a few minutes passed, after one task, a plan, or a progress update. Continue implementation, appropriate verification, evidence recording, and the next actionable task until the requested work is finished or no further authorized work can be performed. Give progress updates without ending longer work. If authorization, access, payment, another person, or external state blocks an action, complete independent authorized work first, then checkpoint and report the precise blocker and next action. Preserve completed progress, financial evidence, and uncertain external effects; respect existing scope, budget, permissions, and safety controls. Never claim unverified completion.

## Business Portfolio checkpoints

- Active canonical records live directly below a niche at `business_portfolio/niches/<niche>/<stable-id>-<slug>/project.md`, with a sibling `work/` folder. There is no intermediate active `projects/` folder. Portfolio Manager shows each project record directly under its niche while keeping its implementation directory out of that navigation. Legacy `projects/*/project.md` and `projects/*.md` are migration inputs only. Stable project and niche IDs survive moves. Keep project-specific source, drafts, assets, tests, builds, releases and marketing material in `work/`.
- Preserve historical archives, manifests, original project bytes, financial evidence and actual external effects. The independent opportunity taxonomy remains research, not an active execution queue. Review the full canonical record, archive crosswalk and latest authorized checkpoint before restoring historical work; never replay uploads, publication, orders or payments from a stale plan. Do not edit immutable archived snapshots to change history.
- Niche folders offer **New project**, **New niche folder**, and **Delete niche**, not a prompt button. New project creates one unique **Empty project** with `workflow_version: 3`, `project_phase: working_phase_1`, `draft: true`, no invented research or sources, and `work/.gitkeep`. New niche creates a child with a stable ID and `working: false`. A confirmed niche deletion removes the whole selected subtree from the active view by moving it to ignored recovery storage; completed receipts and immutable history remain independent. Do not bypass reference or linked-path safeguards.
- Each active category/niche stores its informational `working` boolean in `NICHE.json`. Enabling a child enables its ancestors; a parent cannot be disabled while descendants remain Working. This flag never grants execution authority or changes the project phase. User-created/deleted niches may change the original five-category/25-niche menu; do not recreate deleted folders merely to enforce old counts.
- The four-phase workflow is **1 research (1a product, release and marketing research with verification between each stage; 1b independent verification of all three) → 2 build/test → 3 release → 4 marketing → Complete**. workflow_version 3 distinguishes these meanings from historical numbering. The owner-selected day limit defaults to 21 days and covers the entire project, not each phase. Preserve conditional/deferred/rejected scope and reasons; do not invent completion.
- Phase 1a has niche-research and existing-idea variants. Stage 1 researches buyer value, complete free/native/AI/paid alternatives, sustainable pricing, rights, feasibility, effort, low-downside scope and a detailed implementation specification. Verify the evidence before Stage 2; research alternative candidates if a finalist fails. A bounded TEST-FIRST GO is not verified demand; preserve commercial_validation. Do not force GO, paid buyers, interviews or fabricated evidence. Equally useful free substitutes without material advantage can justify rejection.
- Phase 1a Stage 2 researches promising direct and adjacent compatibility ecosystems and distribution destinations. Add every accepted version to the specification, Phase 2 build/tests and Phase 3 release runbook. Record eligibility, formats, policies, fees, rights, submission/review/update steps, effort and current sources; explicitly classify disproportionate/infeasible routes. Verify Stage 2 before starting Stage 3.
- Phase 1a Stage 3 researches audience/intent, positioning, proof, content, demos, SEO/discovery, permitted communities, partnerships, conversion, measurement and other useful tactics. Add concrete Phase 4 tasks, reconcile the product/release plans and verify all dependencies and the finite initial campaign before finishing the draft.
- Phase 1a produces a complete draft but requires no intermediate paste. Run Phase 1b in the same chat. Paste project text accepts the entire final record; the importer preserves identity, protected metadata, existing work, historical facts, evidence and URLs, checks the copied BASE_SHA256 in project_update_base_sha256 and backs up the original. A verified record automatically advances to Phase 2 in the same transaction only with project_update_phase_1b = "verified", GO, non-draft substantive content, all three research_verification entries approved, valid full sections and source URLs. Temporary fields are stripped. Unverified or failed drafts stay in Phase 1; no phase-control bypass. Structural validation is not independent market verification.
- Phase 1b independently rechecks product, release and marketing with fresh direct sources and counterevidence, corrects real defects and rechecks affected stages. Always return the entire copyable final record even if “Good to go — no substantive changes needed.” Do not force cosmetic revisions or approval of a blocked candidate. Preserve the in-chat draft instead of overwriting it with the appended older disk baseline. Resume unfinished research from checkpoints rather than restarting.
- Selected projects offer Copy research prompt (Phase 1a new product/idea and Phase 1b verification), Copy build prompt (Phase 2), Copy release prompt (Phase 3) or Copy marketing prompt (Phase 4). Research prompts contain the disk record and snapshot hash. Execution prompts are separate Codex /goal requests; finish the assigned phase and its handoff, then stop so the owner can copy the next prompt.
- At every Phase 2, 3 and 4 checkpoint, save completed and remaining tasks, evidence, blockers, decisions, external effects and a concrete next action in project.md. Save and report Phase N completion estimate: X% (best guess), explain its basis and revise it honestly. In migrated records append new estimates below the Four-phase workflow migration heading. Use a meaningful title by Phase 2 while retaining stable ID/path/work.
- Save **any important data and URLs** as they are discovered or created: artifacts, versions/hashes, platform/project/submission IDs, reproducible commands, relevant configuration/results/costs, source/docs/build/preview/live/purchase/download/edit/admin/marketing/support/analytics links, purpose, status and checked date. Preserve retired links as history and distinguish planned destinations from actual live endpoints. Never store secrets, signed token links or private customer/payment data in public project records.
- Codex advances verified execution with python -m portfolio_manager.project_lifecycle set-phase --workflow-version 3 --project "PATH/TO/project.md" --phase working_phase_3 --actor codex --evidence "Actual build evidence" (optional --title "Product Name"); Phase 3 uses working_phase_4 with verified release evidence. The flag prevents obsolete numbered commands. A handoff does not independently verify an external fact. Confirmed owner recovery overrides 2→3 or 3→4 remain explicitly unverified; reconcile prerequisites before external actions. Never bypass Phase 1 verification or manually mark Complete.
- Only after actual Phase 4 marketing and verified releases, Codex obtains real URLs and description and runs set-phase with --workflow-version 3 --phase complete --actor codex --evidence "Actual completion evidence" --description "Factual description" --sale-url "VERIFIED_URL" --marketing-url "VERIFIED_URL" (or --other-url for legitimate public access). Do not ask the owner to type links or mark Complete. The durable business_portfolio/completed_projects/<ID>.json survives source-folder deletion. Demotion revokes a matching receipt; re-completion requires new verification. Completion is independent of sales and commercial validation.
- Use one writer per record and compare expected content before saving. Generated `PROJECT_INDEX.json` / `PROJECT_BROWSER.html` are read-only views, never a second progress database. After producing reviewed, non-sensitive public text, record its `public_results` entry under `business_portfolio/results/<same ID>/`; do not expose paid releases, private receipts/customer data or unreviewed binaries there.
- Git rule: DO NOT create project-specific branches. Coordinate concurrent editors, fetch and reconcile upstream changes, commit and push verified authorized work directly to main, never force-push or overwrite another writer's work. Rebuild with `python business_portfolio/tools/build_browser.py`, run `--check`, the relevant Portfolio Manager regression suite, `python -m unittest discover -s business_portfolio/tests -v`, and `python business_portfolio/tools/commercial_checks.py --portfolio business_portfolio`. Report actual tests and remaining environment limits.
- Creating or pasting a project authorizes planning only. CAD0 current spending and CAD100 cumulative planning ceiling remain distinct; no outreach, ads, accounts, publication, schedules or production actions are authorized merely by a record or phase. Follow real current session authorization and existing Codex/Computer Bridge controls. Preserve financial/customer data outside public records.

## Portfolio Manager

- Portfolio Manager is the primary visual workspace. For “Open the project,” “show the projects,” or “let me see the files,” find the checkout with `git rev-parse --show-toplevel` and call `portfolio_open` through the existing Computer Bridge MCP. If this chat knows the portfolio project it is working on, include its `project_id` or canonical project record `path` so the window opens on that project and displays its name. If the project is unknown, omit both and preserve the existing selection. It starts or reuses the controller and opens this connection's own window. Use `portfolio_context` for “Continue” or questions about the selection. Use `portfolio_select` when the owner requests a different path. Retain the private reconnect key from the first response in chat context so the same workspace can reconnect if MCP restarts. The owner never needs to enter a key.
- When a trusted Portfolio Manager SessionStart hook supplies a reconnect key in its startup context, use that key on the first Portfolio Manager call in the current session. Prefer the current hook context over any key inherited from another conversation. The optional hook must be configured and trusted before it can supply that context.
- For “Continue,” “Work on this,” or questions about the selected item, call `portfolio_context` with this chat's private reconnect key. Work on that file or folder using this normal Codex chat and its normal tools and permissions. Selection alone does not start a worker or authorize an external action. Never alter another chat's selection. For a portfolio project record, read its full canonical record and latest private checkpoint before resuming; use coordinator claims only when coordinating canonical record edits.
- The AI Only / Human Available setting is global across windows and describes owner availability; both modes allow normal chat work. In AI Only, make reasonable decisions and record human-dependent actions for later while preserving normal approvals. Use the integrated Computer Bridge for authorized computer/browser work; keep its Stop and Emergency Stop controls. The legacy worker system is not part of the normal workflow.
