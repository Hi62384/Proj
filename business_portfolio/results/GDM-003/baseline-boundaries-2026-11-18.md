# GDM-003 baseline boundaries and decision — 2026-11-18

**Later correction:** The pause decision below was premature: it compared free tools with a fixture-specific helper but did not perform the plan's comparison against a minimal integrated verifier. The subsequent [integrated spike checkpoint](integrated-spike-2026-11-18.md) preserves this evidence and reopens the feasibility gate; it does not claim a product or commercial advantage.

This continues the controlled [Godot and free-tool baseline](godot-free-baseline-2026-11-18.md). It covers one owned project on one Windows host, using the same Godot 4.7.2 and Dependencies v1.11.1. The earlier result records setup, artifact hashes, and the original cases.

## Additional observations

- **Architecture:** MSVC built an actual x86 version of the fixture extension, and `dumpbin /exports` confirmed its `fixture_init` entry; `dumpbin /headers` showed machine `14C`. Substituting that DLL into the x64 export produced Godot error 193 and `loaded: false`, with process exit 0. This isolates the architecture mismatch more clearly than the prior replacement that lacked the entry point.
- **Misplaced package DLL:** moving `leaf.dll` from the clean output root to `other/leaf.dll` made the game report error 126 and `loaded: false`. Dependencies' JSON showed the leaf unresolved; the fixture-specific script reported the chain and the descriptor's empty destination. It did not independently identify the moved file or prove which search rules applied.
- **Wrong descriptor destination:** a fresh export with the `leaf.dll` dependency destination set to `nested` produced `nested/leaf.dll` and no root-level leaf. Export returned 0; running it reported error 126 and `loaded: false`. Dependencies identified the unresolved chain, while the revised small script displayed the descriptor destination `nested`. This is an observed failure for this fixture and host, not a general claim that every nested library is unresolvable.
- **Host contamination:** adding the clean export directory to `PATH` while examining the missing-leaf package caused Dependencies to resolve `leaf.dll` from that outside directory (search strategy 7). The owned Godot export still reported error 126 and `loaded: false`. The revised script, given the package root, reported that the fixture DLL resolved outside the package and returned 3 for unknown. This one observation does not characterize all Godot or Windows loader settings.
- **Dynamic load:** a separately built owned `dynamic.dll` contains the UTF-16 name `optional-runtime.dll` and imports `LoadLibraryW`. `dumpbin /imports` and Dependencies' `-json -imports` showed `LoadLibraryW`, not a static import of that module. The exported function was not called. Its runtime result and module availability remain unknown.
- **Feature selection:** in a fresh imported project, a generic `windows.release` library entry pointing to a nonexistent file was placed before a valid `windows.release.x86_64` entry. This Godot export returned 0 and staged the valid extension. This single observation does not establish a general tag-selection algorithm; do not flag every descriptor entry as required merely because it is present.

For clean, omitted-dependency, nested-destination, missing-direct and moved-leaf inputs, the revised fixture script returned respectively 0, 1, 1, 1 and 1; the outside-package Dependencies resolution returned 3. It is intentionally tied to the fixture's single-line map and its known source DLL names. It is not a general verifier: it does not parse PCKs or arbitrary Godot configurations, determine architecture, fully model Windows search paths, or recognize dynamic module names. An exit of 0 does not prove a package works. Measured invocations of the already-prepared script took about 95–160 ms on this host; those numbers exclude tool setup, Dependencies analysis, interpretation and authoring, and are not diagnosis-time or product-comparison measurements.

## Decision

**Pause the proposed product implementation at its documented differentiation gate.** The free tools, Godot's export diagnostics, and a small fixture-specific script cover the demonstrated cases and can expose the host-only resolution as uncertain. There is not yet evidence that a maintainable general product provides materially greater value than that combination. The script is not equivalent to the full proposed product, so this is a conditional decision based on the absence of proof, not proof that no worthwhile product is possible. No product, clean-host support matrix, customer demand, price, sale, or commercial validation is established.

The gate can be reconsidered if new, concrete examples show a repeatable engine-specific diagnosis or CI workflow that the free combination cannot reasonably provide, or if the scope and economics are revised. Do not publish, purchase tools, or treat this decision as an authorization for a release. Reproduction inputs are in `products/game-tools/native-dependency-verifier/fixture/`; downloaded third-party tools and generated binaries remain outside the public result.
