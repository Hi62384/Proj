# GDM-002 DIY comparison — 2026-11-18

An independently written fixed-route FIFO implementation was compared with the ledger fixture on the same synthetic input sequence: one cancellation, duplicate cancellation, rejected canceled and duplicate boarding acknowledgments, one missed departure, rejection of a prior-departure token, trusted disk save/restore during boarding, and continuation to 19 arrivals. On Godot 4.5.1, `research/test_negative_comparison.gd` passed and both implementations produced the same 78-event trace. The first DIY version accepted a deliberately corrupt snapshot containing duplicate vehicle ownership, while the ledger fixture rejected it. A subsequent DIY version with basic ownership, capacity and state validation also passed the trace and rejected that corruption (`research/test_validated_comparison.gd`). Both test commands exited 0 and emitted the sandbox root-certificate warning.

The AI-assisted wall-clock interval was approximately 49 seconds for the first DIY implementation and first passing test, and 24 seconds for the later validation addition and test. This includes local tool execution and is not a measured human effort or a fair end-to-end integration comparison: the ledger fixture had no comparable recorded time, and the same AI wrote both with knowledge of the fixed scenario. The DIY versions contain 83 and 114 nonblank, non-comment lines; the ledger schedule and ledger contain 110 and 74. Those counts describe different scopes and do not measure quality or integration cost.

The tests do not implement real NPC navigation, general route planning, a vehicle breakdown, inaccessible stops, or arbitrary controller integration. Native NavigationLink and FlowAI were previously tested as separate graph primitives with the same simple happy-path timetable, not as movement controllers for this negative trace. The technical differentiation gate therefore **has not passed**: several target cases were reproduced by a small alternative, while comparable controller integration and disruption evidence are missing. Do not claim the coordinator saves effort or is ready for a paid release. The next action is a bounded, same-input real-controller and disruption comparison, timed consistently from setup through passing tests, followed by the project's stated go/no-go decision. No spending, publication or sales occurred.

A later fixed-route disruption experiment added the same explicit no-route behavior to both prototypes. In `research/test_disruption_comparison.gd`, the final service is disabled after two passengers board but before departure; both implementations mark all unfinished journeys failed with the same reason and event trace, clear simulated queues/claims/riders, reject a repeated disruption and a late callback, and restore the resulting state. The test passed on Godot 4.5.1. Its first draft incorrectly applied the disruption after the two passengers had arrived, and failed two assertions; the corrected test applies it during the boarding window. This is not a mid-ride breakdown, rerouting, safe physical alighting or real controller integration. It deliberately clears simulated riders immediately, which would need a defined physical recovery policy in a real game.

The DIY comparison and ledger code were both extended for this narrow case in the same session. No consistent end-to-end development or integration timing was collected for either, and those shared implementation conditions limit the comparison. The technical differentiation gate remains unpassed.

The fixed-route ledger and validated DIY fixtures now include a `stranded` state for disruption during transit. Occupied seats remain assigned until an explicit token-checked rescue acknowledgement; scheduled arrival does not silently clear stranded riders. `research/test_midride_comparison.gd` passed a disk restore during the stranded state, stale and duplicate rescue rejection, matching event traces and eventual claim release. This is a simulated policy, not a general rerouter; the disruption conservatively affects all unfinished journeys and the caller must arrange physical recovery. The ledger snapshot format is now version 3 and rejects earlier fixture versions; no migration is provided.

One actual `CharacterBody3D` with native `NavigationAgent3D` traversed the same three-stop path using each fixture. Both completed the two-leg trace in 178 physics frames and two link callbacks. A separate interruption test brought the body back to a designated safe point before rescue; both produced the same three-event trace in 57 frames. With FlowAI commit `f0fca85e3222cc2ad42d9668eb22006b149e1d71`, the corresponding one-body normal and interrupted tests also passed for both implementations (178 and 58 frames respectively), using positional thresholds for boarding. FlowAI reported ObjectDB and three resource warnings at shutdown. Its first normal test failed the target-distance check with the default path tolerance; a rerun with `path_desired_distance = 0.15` passed.

These are one-passenger, shared-controller experiments. There is no vehicle physics, collision obstacle, timed waiting in the navigation controller, second controller pattern, measured integration effort or multi-agent real-navigation run. Both implementations passed the selected cases, so no reliability or effort advantage has been demonstrated. The differentiation gate remains unpassed. Eight affected ledger/native scripts passed in the final batch; Godot continued to warn that it could not read the root certificate store. The FlowAI tests were run separately and are reproducible using the research README.

Twenty-body tests were subsequently run with both Godot NavigationAgent3D and FlowAI controllers. For each controller, the ledger and validated DIY fixtures completed 20 journeys in 49 schedule ticks and produced the same 80-event trace. A separate interruption test for each controller verified that three boarded bodies were physically between stops, moved them directly back to a designated safe point, acknowledged rescue and compared the same 26-event trace. Both implementations passed. The native happy-path runs printed 9.805 and 9.799 seconds; FlowAI printed 9.680 and 9.796 seconds. These are physics-frame-driven test durations on one machine, not an engineering-effort measurement or a performance benchmark. FlowAI again emitted ObjectDB and three resource warnings on shutdown.

The comparison uses one shared, AI-authored test adapter with minor API branching and a fixed, known scenario. The bodies have no collision obstacles or vehicle physics; boarding is acknowledged immediately by the test, and the emergency return is direct movement rather than pathfinding. No automated controller-state disk restore was run in the 20-body tests, and no equivalent setup or QA time was measured. The observed matched behavior provides no demonstrated technical advantage for the candidate on these scenarios. The required differentiation gate remains unpassed; these results do not prove the alternative solves every intended use. See the research README for exact scripts and reproduction.

The subsequent 20-body native and FlowAI tests saved each fixed schedule plus body positions, intended targets and moving flags to trusted local disk while riders were physically between stops. They destroyed and reconstructed the bodies and navigation agents, then continued to 20 arrivals. Each ledger and DIY trace matched the original unrestored 80-event reference. The initial native draft failed because its checkpoint was taken after movement ended; the passing version checkpoints earlier and asserts the bodies are between stops. FlowAI again reported ObjectDB and resource warnings at exit. This test reconstructs only the specified synthetic controller inputs and a fixed navigation graph, not arbitrary game state or a safe general-purpose save format.
