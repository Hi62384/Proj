## ProjectBridge delivery modes — choose based on the request

- **Codex, IDE agents, local coding agents, and any agent working in a writable checkout:** **edit files directly** using the normal coding workflow, then test and report results. **Do NOT produce `ProjectBridge_patch.zip`** unless the user specifically requests it. The presence of these instructions does not mean ZIP delivery was requested.
- **Normal ChatGPT reading GitHub read-only, without a writable checkout:** for coding-change requests, **default to a ProjectBridge patch ZIP** unless the user requests another output. Read `PROJECTBRIDGE_PATCH_INSTRUCTIONS.md` **in full** before building a ZIP, then package only the relevant changes against the GitHub baseline.
- For all other tasks, use the tools and delivery format explicitly requested by the user. Never replace direct Codex edits, commits, or PRs with a ZIP without the user asking.
- Preserve project-specific build/optimization instructions elsewhere in `AGENTS.md`. Report tests honestly.

## Project execution persistence

- When the owner asks you to work on this project, continue autonomously through all remaining authorized tasks possible with available access and resources. Do not stop merely because a few minutes passed, after one task, a plan, or a progress update. Continue implementation, appropriate verification, evidence recording, and the next actionable task until the requested work is finished or no further authorized work can be performed. Give progress updates without ending longer work. If authorization, access, payment, another person, or external state blocks an action, complete independent authorized work first, then checkpoint and report the precise blocker and next action. Preserve completed progress, financial evidence, and uncertain external effects; respect existing scope, budget, permissions, and safety controls. Never claim unverified completion.

## Business Portfolio checkpoints

- Active canonical records live directly below a niche at `business_portfolio/niches/<niche>/<stable-id>-<slug>/project.md`, with a sibling `work/` folder. There is no intermediate active `projects/` folder. Portfolio Manager shows each project record directly under its niche while keeping its implementation directory out of that navigation. Legacy `projects/*/project.md` and `projects/*.md` are migration inputs only. Stable project and niche IDs survive moves. Keep project-specific source, drafts, assets, tests, builds, releases and marketing material in `work/`.
- Preserve historical archives, manifests, original project bytes, financial evidence and actual external effects. The independent opportunity taxonomy remains research, not an active execution queue. Review the full canonical record, archive crosswalk and latest authorized checkpoint before restoring historical work; never replay uploads, publication, orders or payments from a stale plan. Do not edit immutable archived snapshots to change history.
- Niche folders offer **New project**, **New niche folder**, and **Delete niche**, not a prompt button. New project creates one unique **Empty project** with `workflow_version: 2`, `project_phase: working_phase_1`, `draft: true`, no invented research or sources, and `work/.gitkeep`. New niche creates a child with a stable ID and `working: false`. A confirmed niche deletion removes the whole selected subtree from the active view by moving it to ignored recovery storage; completed receipts and immutable history remain independent. Do not bypass reference or linked-path safeguards.
- Each active category/niche stores its informational `working` boolean in `NICHE.json`. Enabling a child enables its ancestors; a parent cannot be disabled while descendants remain Working. This flag never grants execution authority or changes the project phase. User-created/deleted niches may change the original five-category/25-niche menu; do not recreate deleted folders merely to enforce old counts.
- The six-phase workflow is **1 product research/specification → 2 release platforms/compatible versions → 3 marketing research → 4 build/test → 5 release → 6 marketing → complete**. `workflow_version: 2` distinguishes these meanings from historical phase numbers. New work across all phases should fit the owner-selected project day limit, which defaults to 21 days; this is one shared limit, not a new window per phase. Broad research must lead to a finite feasible accepted scope, with conditional/deferred/rejected routes and reasons preserved. Do not invent completion to fit the deadline.
- Phase 1 has separate niche-research, existing-idea and verification prompts. Research buyer value, complete free/native/AI/paid alternatives, sustainable pricing, rights, feasibility, owner effort and low-downside scope; produce a detailed implementation specification and acceptance criteria. A TEST-FIRST GO recommends a bounded experiment, not verified demand for an unreleased offer. Preserve `commercial_validation`; future first sales/conversion are testable assumptions, not automatic prelaunch failures. Do not force GO, paid buyers, interviews or fabricated evidence. A complete equally useful free substitute without material advantage remains a legitimate reason to reject.
- Phase 2 has separate release research and verification prompts. Research all promising appropriate direct and adjacent compatibility ecosystems plus distribution destinations. Every accepted version must be added to the Phase 1 specification, Phase 4 build/tests and Phase 5 release runbook. Record eligibility, formats, policies, fees, rights, submission/review/update steps, effort and current sources. Classify infeasible or disproportionate targets explicitly rather than silently committing to unlimited ports.
- Phase 3 has separate marketing research and verification prompts. Research audience/intent, positioning, proof, content, demos, SEO/discovery, permitted communities, partnerships, conversion, measurement and other useful tactics beyond a platform list. Add concrete Phase 6 tasks, adapt earlier build/release plans only where justified, and preserve actual completed work. The initial campaign must be finite and achievable within the remaining project window.
- All Phase 1–3 research returns **complete copyable project text**, not a mandatory downloadable file or repository edit. **Paste project text** replaces the selected research record after strict metadata, identity, stale-content and schema checks, with a local backup. Planning sections may be reorganized or corrected; preserve historical facts, completed work, all important data/URLs and protected financial/permission fields. Include the copied `BASE_SHA256` as `project_update_base_sha256`; Portfolio Manager strips it. Pasting never advances the phase. The user manually advances sequentially 1→2→3→4 after reviewing the research/recheck.
- Verification prompts must test the evidence, not manufacture changes. If no material revision is warranted, answer **“Good to go — no substantive changes needed.”** and give concise sourced verification; do not emit an unnecessary replacement record. Minor wording or optional features must not force rewriting or replacement. Real defects require justified revisions; decisive blockers remain explicit. Repeated prompts request separate bounded reviews, not an endless internal loop.
- Selected project prompt labels identify the task: **Copy research prompt**, **Copy release research prompt**, **Copy marketing research prompt**, **Copy build prompt**, **Copy release prompt**, or **Copy marketing prompt**. Phases 1–3 include the complete current record and snapshot hash for ChatGPT. Phases 4–6 are separate Codex `/goal` prompts. Finish only the assigned phase, perform its handoff, then let the user copy the next prompt; do not silently execute the next phase.
- At **every Phase 4, 5 and 6 checkpoint**, save completed `[x]` and remaining `[ ]` work, evidence, blockers, decisions, external effects and one concrete next action in project.md. Save and report the exact line `Phase N completion estimate: X% (best guess)` for the current phase, even when uncertain; explain the basis and revise it honestly. Estimates are not observed completion evidence. Rename an Empty project to a meaningful product display title by Phase 4 while retaining ID/path/work.
- Save **any important data and URLs** as they are discovered or created: artifacts, versions/hashes, platform/project/submission IDs, reproducible commands, relevant configuration/results/costs, source/docs/build/preview/live/purchase/download/edit/admin/marketing/support/analytics links, purpose, status and checked date. Preserve retired links as history and distinguish planned destinations from actual live endpoints. Never store secrets, signed token links or private customer/payment data in public project records.
- Codex advances completed execution phases with `python -m portfolio_manager.project_lifecycle set-phase --project "PATH/TO/project.md" --phase working_phase_5 --actor codex --evidence "Actual Phase 4 evidence"` (optional `--title "Product Name"`); then Phase 5 uses `--phase working_phase_6` with its evidence. A phase change records the handoff; it does not independently test a build or verify an external URL. Required incomplete/blocked tasks remain in their phase unless a justified explicit scope revision changes the accepted work.
- Only after actual Phase 6 marketing and verified releases, Codex obtains the real URLs and factual description and runs `--phase complete --actor codex --evidence "Actual completion evidence" --description "Factual description" --sale-url "VERIFIED_URL" --marketing-url "VERIFIED_URL"` (or `--other-url` for legitimate public access). Do not ask the owner to type links or mark Complete. The durable `business_portfolio/completed_projects/<ID>.json` survives source-folder deletion and appears read-only. Demotion revokes the matching receipt; re-completion needs new verification. Completion is independent of paid sales and commercial validation.
- Use one writer per record and compare expected content before saving. Generated `PROJECT_INDEX.json` / `PROJECT_BROWSER.html` are read-only views, never a second progress database. After producing reviewed, non-sensitive public text, record its `public_results` entry under `business_portfolio/results/<same ID>/`; do not expose paid releases, private receipts/customer data or unreviewed binaries there.
- Git rule: DO NOT create project-specific branches. Coordinate concurrent editors, fetch and reconcile upstream changes, commit and push verified authorized work directly to main, never force-push or overwrite another writer's work. Rebuild with `python business_portfolio/tools/build_browser.py`, run `--check`, the relevant Portfolio Manager regression suite, `python -m unittest discover -s business_portfolio/tests -v`, and `python business_portfolio/tools/commercial_checks.py --portfolio business_portfolio`. Report actual tests and remaining environment limits.
- Creating or pasting a project authorizes planning only. CAD0 current spending and CAD100 cumulative planning ceiling remain distinct; no outreach, ads, accounts, publication, schedules or production actions are authorized merely by a record or phase. Follow real current session authorization and existing Codex/Computer Bridge controls. Preserve financial/customer data outside public records.

## Portfolio Manager

- Portfolio Manager is the primary visual workspace. For “Open the project,” “show the projects,” or “let me see the files,” find the checkout with `git rev-parse --show-toplevel` and call `portfolio_open` through the existing Computer Bridge MCP. If this chat already knows its current canonical project record, pass its path to `portfolio_open` so the window opens on that project; otherwise preserve the existing selection. It starts or reuses the controller and opens this connection's own window. Use `portfolio_context` for “Continue” or questions about the selection. Use `portfolio_select` when the owner requests a different path. Retain the private reconnect key from the first response in chat context so the same workspace can reconnect if MCP restarts. The owner never needs to enter a key.
- When a trusted Portfolio Manager SessionStart hook supplies a reconnect key in its startup context, use that key on the first Portfolio Manager call in the current session. Prefer the current hook context over any key inherited from another conversation. The optional hook must be configured and trusted before it can supply that context.
- For “Continue,” “Work on this,” or questions about the selected item, call `portfolio_context` with this chat's private reconnect key. Work on that file or folder using this normal Codex chat and its normal tools and permissions. Selection alone does not start a worker or authorize an external action. Never alter another chat's selection. For a portfolio project record, read its full canonical record and latest private checkpoint before resuming; use coordinator claims only when coordinating canonical record edits.
- The AI Only / Human Available setting is global across windows and describes owner availability; both modes allow normal chat work. In AI Only, make reasonable decisions and record human-dependent actions for later while preserving normal approvals. Use the integrated Computer Bridge for authorized computer/browser work; keep its Stop and Emergency Stop controls. The legacy worker system is not part of the normal workflow.
